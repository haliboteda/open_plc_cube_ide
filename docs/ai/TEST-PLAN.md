# 测试框架

**怎么证明 [REQUIREMENTS.md](REQUIREMENTS.md) 里的每一条。** 建于 2026-08-17。

## 三条原则（沿用 [../BUILD-AND-TEST.md](../BUILD-AND-TEST.md)）

1. **测真实代码路径。** 需要"传输进行中"的用例把 IAPTool 当子进程拉起来跑真实烧写，不自己实现传输。
   > 教训：手写的探测脚本能正常读到设备，掩盖了 IAPTool 自己的真 bug，直到用真实工具跑完整流程才暴露。**一次性脚本测的是它自己的逻辑。**
2. **加密逻辑 import，不重写。** 负向用例只把该错的那一处弄错，其余全用出货代码。
3. **反向用例和正向用例一样重要** —— "不该发生的事没发生"最容易漏，而且只在现场暴露。

## 四层，由快到慢

**前一层不过就不要往下走。** 上板调试的每一轮都比主机测试贵一个数量级。

| 层 | 跑什么 | 要板子 | 耗时 | 一条命令 |
|---|---|---|---|---|
| **0 静态** | P1–P3 | 否 | 秒 | `tools\selfcheck.ps1` 的一部分 |
| **1 主机** | H1 H2 K1–K6 X1 X2 | 否 | 约 2 分钟 | **`tools\selfcheck.ps1`** |
| **2 构建烧写** | T0 + 尺寸门禁 | 是 | 分钟 | `tools\flash-bootloader.ps1` |
| **3 设备行为** | T/N/S/G | 是 | 十分钟量级 | `TestTool all --ip=<板子IP>` |
| **4 人工** | S4a S4b M3 O1 | 是 + 人 | — | 见下面各条 |

用例的**判据和运行方法**在 `$TOOL/TestTool/README.md`（贴着代码走，跨仓不搬）。这份文档管**覆盖矩阵**、**待补用例的完整设计**和**最近结果**。

## 待补用例的完整设计

下面每条按同一骨架写全，落地时照抄即可。**没写实际结果的就是没跑过**，不要填"应该没问题"。

### S2 · 密钥不匹配

| | |
|---|---|
| **目的** | 分开验证"签名坏了"和"签名是别人签的"。两者现象都是"拒绝启动" |
| **覆盖需求** | C2 |
| **前置条件** | 设备停在 bootloader；手上有一把**和板子里公钥不配**的私钥 |
| **步骤** | 1. 用不匹配的私钥签一个结构完整的镜像<br>2. 绕过 IAPTool 的 `getpubkey` 预检直接送上去（做法同 S1）<br>3. 复位 |
| **预期** | 上传阶段回 `Signature Failed`；复位后旧 app 照常启动（app 区未被碰） |
| **验证方式** | TestTool 用例，加密部分 import `IAPTool/iapcrypto` |
| **实际结果** | — |
| **结论** | — |

> **为什么必须和 S1 分开**：混在一起测过一次，结果把一次密钥轮换误判成校验代码的 bug。

### M3 · 两块板的 MAC 不同

| | |
|---|---|
| **目的** | MAC 从 UID 派生的算法**"两块板不同"从未被观察过**。派生有缺陷的话，量产时表现为同网段大面积 IP 冲突 |
| **覆盖需求** | E1 |
| **前置条件** | ⛔ **第二块板**。这是唯一的阻塞项 |
| **步骤** | 1. 两块板同网段同时上电<br>2. 各自抓串口，记下 bootloader 和 app 两侧打印的 MAC<br>3. 比对四个值 |
| **预期** | 两块板的 MAC 不同；同一块板的两侧相同 |
| **验证方式** | 人工，两路串口 |
| **实际结果** | — |
| **结论** | — |
| **配套** | 产线要留 MAC 记录，否则"不重复"无从判起（`acceptance/checklist.md` C3） |

> **现在就能做的部分**：P2 已经自动比对了两侧派生算法的一致性。剩下的只有"算法本身会不会撞"，那需要真的两块板。

### AU1 · 板上 nonce 跨掉电不重复

| | |
|---|---|
| **目的** | 重放保护靠的是 nonce **唯一**（不是不可预测）。计数器存在 RTC 备份寄存器里，靠 VBAT 保持 |
| **覆盖需求** | **C5** —— 目前完全没有测试覆盖 |
| **前置条件** | 设备可发起 `authchallenge`；VBAT 电池在位 |
| **步骤** | 1. 连发 N 次 `authchallenge`，记下每个 nonce<br>2. 断电、重新上电<br>3. 再发 N 次，记下 nonce<br>4. 检查 2N 个 nonce 的前 4 字节（计数器部分）**严格递增且无重复** |
| **预期** | 无重复；掉电后接在旧序列上继续，不归零 |
| **验证方式** | TestTool 新用例，走真实协议 |
| **实际结果** | — |
| **结论** | — |
| **为什么值得做** | 2026-08-17 刚发现过一个真实缺陷：bootloader 的 witness 和 app 的计数器都占 `DR2`，**每次经过 bootloader，app 就重复发放同一批 nonce**。这个用例能直接抓到那类问题，而当时是靠肉眼看日志发现的 |
