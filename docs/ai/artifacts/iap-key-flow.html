IAP · 挑战-响应鉴权

iap_fixed_password 是怎么用的

一份固定密码，混合每台设备自己的 UID，派生出各不相同的设备密钥； 整个校验过程只比对 HMAC 摘要，密码本身从不上线传输。

存放位置

Bootloader IAPServer/iap_keyderive.c 编译进 bootloader 的 .bin，随 bootloader 一起烧录，运行时常驻 Flash。
Arduino App OpenPLC_Net/src/iap_keyderive.c 编译进用户 App 的 .bin，随正常草图上传一起烧录。
PC 工具 iapcrypto.FixedPassword 编译进 IAPTool 可执行文件的常量，不是配置文件、不可运行时更改。

三处必须逐字节完全相同，否则设备与工具算出的密钥不一致，握手必然失败。

握手 & 校验流程

怎么"比对"的

从头到尾，iap_fixed_password 本身从未在网络/串口上传输，也从未被"比对"过—— 真正被比较的是两次独立算出的 HMAC 摘要：

PC 工具这边：先问到设备 UID，本地算出 deviceKey，再用这个 key 对"即将发送的命令原文"算一次 HMAC，随命令一起发过去。

设备这边收到命令后，不会相信也不会使用命令里附带的任何密钥信息——它只用自己内部的 HAL_GetUIDw0/1/2() 重新读一遍自己的 UID，加上自己 Flash 里那份 iap_fixed_password，独立地重新推导出同一个 device_key， 再对它自己刚刚解析出来的命令参数重新拼出 nonce‖msg 算一次 HMAC。

最后调用 constant_time_eq() 逐字节异或比较两段 32 字节摘要——用恒定时间比较而不是 memcmp，是为了不让"比较提前退出的时间差"泄露出摘要匹配到了第几个字节， 堵住一种旁道计时攻击。

是否随 bootloader 一起烧写？

是的。iap_fixed_password 是 C 里的 static const 数组， 编译期就被放进 .bin 的代码/常量段，和其余固件代码一起被 IAPTool 或 ST-Link 写入 Flash—— 没有单独的"写密钥"步骤，正常烧录 bootloader / App 就已经把它带进去了。

这解决了什么，没解决什么

解决了"全体设备共用同一把 key"的问题：现在不同设备算出的 HMAC 不同。 但 iap_fixed_password 本身仍是三份代码里写死的同一个占位值， 而 UID 又是 getuid / discovery 回复里明文可读的—— 谁只要拿到这个密码常量（反编译固件或 PC 工具都能拿到）+ 目标 UID， 就能替任意一台设备算出它的 device_key。 真正的产线级方案仍是"每台设备一个独立生成、不可从公开信息反推的密钥"。
