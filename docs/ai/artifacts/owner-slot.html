OpenPLC · STM32H743 · owner 槽设计

板子归谁

出厂默认根的私钥必然是公开的——这是产品定位推出来的，不是妥协。 于是真正要设计的不是"开箱怎么安全"，而是客户手上那块没有 ST-Link 的板子，靠什么把信任根换成自己的。 答案是一个只追加、永不擦除的 owner 记录区，寄生在 bootloader 扇区尾部——净增 0 个 flash 扇区。

为什么默认根的私钥只能是公开的

  1. 客户下载 Arduino 包，写自己的 PLC 程序并上传
  2. 上传要签名 → 签名要私钥 → 私钥得在客户的机器上
  3. 项目开源，不给客户发任何专属材料
  4. ⇒ 那把私钥必须在开源仓库里 ⇒ 公开

反过来假设：如果出厂根的私钥是厂商的秘密，客户就只能跑官方签的固件，不能跑自己写的 sketch——产品没了。

所以出厂状态必然不设防，问题只剩两个

① 客户知不知道自己现在不设防？
② 客户想加固时，有没有一条不用 ST-Link 的路？

第二条是 owner 槽存在的全部理由。如果根只能编译进 bootloader， 一个没有 CubeIDE、没有 ST-Link 的客户，手上那块板子一辈子只认公开密钥。

它住在哪：寄生在 bootloader 扇区尾部

H743 的擦除粒度是整个 128K 扇区，没有更小的。所以任何"独立生命周期"的 flash 区域最少要 128K—— 除非它寄生在一个已经被占用、但没用满的扇区里。

顺带绕开了一个常量陷阱

RESERVED_TAIL_SECTORS 在代码里被当成两个不同的意思用： usbd_cdc_flash.c:237 当它是"尾部预留几个扇区"， bootloader_state.c:317 当它是"reclaim 擦几个扇区"。 而 IAP_APP_MAX_SIZE 直接由 IAP_STATE_SECTOR_ADDR 算，根本不看它。

预留 1 个扇区时三处恰好自洽；改成 2 就会散架，而且没有任何一处会编译报错。 走 bootloader 尾部这条路完全不用碰它——但这个重载本身仍然是颗地雷， 下一个想加尾部扇区的人还会踩，值得单独修掉。

启动时怎么决定用哪把根

这个状态机和 UEFI Secure Boot 是同构的

owner 区为空 = UEFI 的 Setup Mode（没有 Platform Key，谁都能写）； 认领 = 写入 PK 进 User Mode； 换 owner 必须被当前 owner 签名 = 改 PK 必须被 PK 签名； cleared 记录 = 删除 PK 回 Setup Mode，需要物理进固件设置界面。

建议直接借用这套术语写文档——读者有现成的心智模型，不用从头解释。

三个操作各自改了什么

owner 区是只追加的，和 journal 同一个路子。 因为它和 bootloader 共处一个扇区，三个操作里没有任何一个会擦除——连恢复出厂都不擦。

规则内容挡住什么挡不住什么
R1 认领必须按住 BOOT0 远程顺手接管一块出厂板子 出厂状态下上传一个恶意 sketch 去直接写这片区域
R2 换 owner 必须由当前 owner 根签名 已认领的板子被任何人夺走，包括有 flash 写权限的代码 —
R3 恢复出厂（追加 cleared）必须物理动作 远程把别人的板子降级回公开根 有物理接触的人恢复出厂后接管
R4 撤销只针对叶子编号，永远不能撤到一个有效根都不剩 把自己撤成永久变砖 —

R3 挡不住的那一条必须接受——keys/README.md 已经把"防不住手里拿板子的人"写成了设计前提。 反过来如果不给恢复出厂，客户丢了自己的根就是永久变砖，而他恰恰没有 ST-Link。

R4 不是假想。ESP32 Secure Boot v2 的 aggressive revoke 就是一个真实的反面教材—— Espressif 官方文档自己写着，签名校验失败触发撤销时"could also brick the device permanently if all the keys are revoked"。

整张表最后一列全是"不用"

owner 槽完全活在 bootloader 里，Arduino core 一行都不用改。 认领命令由 bootloader 处理（它本来就要求 BOOT0 物理按键，那时 app 根本没在跑）， 所以不涉及 core 的 OpenPLC_IAP、不涉及跨仓镜像、不用重新分发板卡包。

这和会话认证形成对比——那个一旦改成证书，core 侧的 iap_keyderive 必须跟着改。 两件事的成本差一个数量级，这应该影响实施顺序。

证书为什么可以留在 journal 里：它只需要能验证当前那个 app，而 journal_reclaim() 只发生在 save_metadata() 内部——擦完立刻就有一条新 M 记录带着新证书写进去。 只有 owner 根和撤销状态需要免疫 reclaim，证书不需要。

owner 记录长什么样（提案）

沿用 journal 的 32 字节 flash word 粒度，一条记录 5 个字 = 160 字节。 

偏移  长度  字段              说明
────────────────────────────────────────────────────────────────
  0     1   type              'O' = owner 记录，0xFF = 空
  1     1   slots             5
  2     2   format_ver        1
  4     4   generation        单调递增，G1=1、G2=2…… 最大的那条有效记录获胜
  8     4   flags             bit0 = cleared（恢复出厂标记）
 12    64   root_pubkey       这一代 owner 的根公钥（secp256r1 X‖Y）
                              cleared 记录里全 0
 76    64   prev_sig          由上一代根对本记录前 76 字节的签名
                              G1 没有上一代 → 全 0，即 TOFU
                              cleared 记录同样全 0，靠物理动作门控
140    20   reserved
────────────────────────────────────────────────────────────────
                              160 字节 = 5 × 32 字节 flash word

用 _Static_assert 锁死尺寸——这些尺寸就是 on-flash 格式， 多一个 padding 字节会让已经写进去的每条记录全部错位，所以让它编译失败而不是运行时才发现。 format_ver 从第一版就要有：将来任何格式演进才不会变成一次破坏性迁移。

诚实的上限

owner 槽的安全上限 = "这块板子上能不能跑任意代码"

出厂状态：能。默认根私钥公开 → 谁都能签 sketch → 谁都能写 owner 区 → R1 的 BOOT0 要求 只保护"受支持的那条路"，不构成密码学保证。第一次认领本质上是先到先得。

已认领之后：不能。要让代码跑起来得先过签名，而签名要 owner 的私钥。 从这一刻起 R2 是真正的密码学保证。

所以文档里要写死一句话：板子到手第一件事是认领。在此之前它和一块没上锁的板子没有区别—— 而这一点无论做不做 owner 槽都成立，owner 槽只是第一次给了它一条上锁的路。

ST-Link 重烧 bootloader = 所有权重置

owner 记录和 bootloader 共处一个扇区，所以重烧会把它们一起擦掉。 语义上这是对的——能 ST-Link 的人本来就能恢复出厂（R3 已经接受了这一点）。

但它和已有的「bootloader 与 app 必须捆绑升级」风险叠加： 换 bootloader 的人要同时重传 app 和重新认领。发布说明里这两条要写在一起。

还没定影响什么
保留 4K / 8K / 16K 决定能存多少条记录，以及给未来的证书验证代码留多少余量。撤销状态也要住进来
要不要上 WRP 写保护 唯一能真正禁止 app 写这片区域的手段。H7 的选项字节改动需要解锁并复位，代价和收益都要评估
认领时要不要绑 UID 把 owner 记录和这块板的 UID 绑死，防止把一块板的记录整段搬到另一块板上
恢复出厂的触发方式 BOOT0 长按已经被"进上传模式"占用，需要一个能区分开的动作（更长时间？上电时按住？）
会话认证换不换成证书 换了就消掉固定密码的三边镜像和"产线单板密钥"那条推迟项，但要动 core，成本高一个数量级
