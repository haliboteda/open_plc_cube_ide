方案 B 实施计划

七个阶段，前三个互相独立可以任意顺序做，后四个是链式的。 每个阶段都能单独验证。全程零 .ioc 改动。

阶段 2 — SDRAM 暂存

阶段 2 SDRAM 暂存 风险最高 无依赖 需要你实测

把擦除时机从「收到 flash 命令时」推迟到「验签通过后」。收到的镜像先进 SDRAM， 全部收完算 CRC + SHA-256 + 验签，通过了才擦 flash 并写入。

  • 失败的升级不再毁掉运行中的 app —— 断网、断电、传输错误、被攻击打断，app 一直在跑
  • 只有 OPEN_SESSION 的人再也擦不掉 app —— 他签不出有效固件，根本走不到擦除那一步
  • SDRAM 是 AS4C32M16SB，64 MB；app 最大 1.75 MB，36 倍余量
  • FMC 已在 Phase 2 初始化，跑 app 那条路径不碰，无污染；升级完是 SystemReset，不用 de-init

风险来源：这是 IAP_data_recv / process_command 主数据路径的重构， 协议不变（还是边收边回 OK），但落盘时机变了。建议单独做、单独测，不要和别的混在一起。

你要做的：① 正常升级 ② 传到一半拔网线 → app 应该还在跑 ③ 故意用错误的签名升级 → 应该拒绝且 app 完好 ④ 传一个接近 1.75 MB 的大镜像

阶段 3 — 证书

阶段 3 证书 硬切换 需要你决策 + 实测

板子侧

  • 160 字节定长证书，无解析器；device_uid 在签名覆盖范围内
  • cert_verify()：magic / version / serial / caps / uid 检查 + 根验签
  • 两个根公钥槽位，root_disabled 位；caps 默认全给；device_uid 默认全零
  • metadata 记录加 cert[160]，journal 槽位 128 → 512 字节
  • 事件日志记 cert serial（占用 reserved 区，不改大小）
  • 验签前先做便宜的格式检查（magic / 长度），不对直接丢，不进 ECDSA

app 侧（Arduino core）

  • 同期加 uECC + cert_verify —— 每个用户 sketch 约 +8~10 KB
  • 不做的话，老 app 认不了新叶子，网口进不去，只剩柜子里的按钮

PC 侧

  • Go 共享包 iapcert（证书格式唯一实现）
  • IAPCert 最小可用版：init（生成两把根）、issue（签发叶子）
  • __has_include + #error 强制先生成密钥；保留测试密钥 + -DIAP_ALLOW_TEST_KEY 逃生开关 + 运行时持续警告

槽位从 128 变 512，旧 journal 必须整扇区擦掉

新 bootloader 会把旧格式的数据当新格式解析，得到荒谬结果。 journal 要加一个格式版本标记，识别不出就整扇区擦除重来。 这是安全的：旧 metadata 里没有 cert，对新 bootloader 本来就没用。

你要决策：① sha256 字段留不留（验签用不到，我建议留做取证，空间够）
你要做的：ST-Link 重烧 bootloader + 重推 app（这是最后一次因为换钥匙而重烧），然后全流程实测

阶段 4 — 撤销

阶段 4 撤销 需要你决策 + 实测
  • 黑名单：独立 journal 记录（不放 metadata 里，一次固件升级不该有能力影响撤销状态），一条记录存完整快照，126 个 serial
  • min_serial 底线：板子端 3 行；compact 是工具端命令，撞满时提示但不自动执行
  • 撤销只能根私钥直接签，不经过叶子；不支持通配符；禁用根 A 必须由根 B 签
  • 撤销只管刷写，不管上电验证 —— 否则一撤销全场停机
  • reclaim 必须保住撤销记录和根禁用位，只丢纯事件日志。这是罕见路径 + fail-open，必须专门写测试
  • app 也查撤销，否则作废的叶子能反复重启板子把 PLC 打瘫。journal 读取做成单份共享 .c
  • getstatus 只返回撤销名单的哈希，不返回明细（不给攻击者指路）
  • 撤销文件永远是完整快照不是增量，幂等；随升级带上（零停机）或独立推送（几秒停机）
你要决策：① 黑名单容量（126 = 一年 2 次撤销可用 60 年，我建议就这个）
你要做的：实测撤销 → 被撤销的叶子刷不进去 → 但已装固件继续运行； 专门测 reclaim（写满 journal 后撤销记录还在）

阶段 6 — profile 多根分支

阶段 6 profile 多根分支 纯工具侧 · 可延后

你有多个下游客户，每家一套独立的根，设备不交叉。

  • keys/<profile>/ 各自持有根、台账、撤销文件
  • IAPCert use <profile> 把该 profile 的 root_pubkey.inc 装进 CubeIDE 项目 + Arduino core
  • IAPCert status 显示项目当前装的是哪个 profile
  • profile 名字编进固件，启动 banner 打印

最大风险：切错 profile，给客户 A 的板子烧上客户 B 的根

因为根公钥是编译进 bootloader 的，每个 profile 必然对应一个独立的 build，烧录时可能搞混。 三道防线：banner 打印 profile 名、IAPCert status 可查、以及 getpubkey 兜底 —— 刷 bin 时工具会发现根不匹配并拒绝，不会静默出错。

你要决策：这次做还是以后做（不影响板子侧，随时可加）

三个最高风险点

风险为什么危险怎么控
SDRAM 暂存 主数据路径重构，改的是每次升级都走的代码 单独一个阶段做，单独测，不和别的混
reclaim 保撤销 罕见路径（写满 256 条才触发），出错方向是 fail-open，可能几年不被发现 专门写测试，人为灌满 journal 验证
app 侧 +10 KB 改变每个用户 sketch 的体积和行为，影响面最广 H743 有 2 MB flash，余量充足；但要在文档写明不是零成本
