Two Keys, Two Jobs

The IAP path runs two completely independent key systems. An ECDSA P-256 keypair decides what is allowed to run; a shared password plus each chip's UID decides who is allowed to start an update. They never touch each other, and they live in very different places.

What each one actually decides

They are not two keys for two stages of one check. They are two different questions, and neither answer implies the other. An update has to pass both, at opposite ends of the transfer.

Where the key material sits

That asymmetry is the reason the two live in such different places. The ECDSA private key never enters the flash image — only its signature crosses. The fixed password does the opposite: the exact same bytes are compiled into the firmware and into the PC tool.

The flash exchange, command by command

CDC (USB serial) and Ethernet (TCP) run the identical command sequence — only the transport differs, and the Ethernet path adds an HMAC-authenticated openplc_server_reboot first to get the running app back into the bootloader. Every command is newline-framed.

getversion sits between the key match and the challenge. It is advisory only: the tool compares the image's .version against what the board reports and prompts the operator on a downgrade. The bootloader itself never refuses a downgrade.

What happens at every boot

The signature is not checked only at update time. Every reset re-hashes the app region and re-verifies it against the signature stored in the metadata journal, before a single peripheral beyond UART4 has been brought up.

Every point that can refuse

  • iap_auth.c Crypto self-test failed at boot — every HMAC and signature result is treated as failed rather than trusted to a primitive already known broken.
  • IAP_server.c · flash Size out of range, or signature hex malformed — refused before the erase, so a bad upload never destroys the installed app for nothing.
  • iap_auth.c No pending nonce, nonce expired, or nonce already consumed — one-shot, consumed whether the check passes or fails. Logged as IAP_EVT_AUTH_FAIL.
  • iap_auth.c HMAC mismatch — constant-time compare against HMAC(deviceKey, nonce || command).
  • IAP_server.c · after transfer CRC32 mismatch — IAP_EVT_CRC_FAIL, no metadata written.
  • fw_verify.c ECDSA verification fails — IAP_EVT_SIG_FAIL, no metadata written, so the next boot will not run the image either.
  • IAPTool · auth.go Board's public key differs from the local signing key — refused up front, before the transfer. A board too old to answer getpubkey only warns.
  • server_decide() App signature invalid or absent at boot — IAP_EVT_BOOT_VERIFY_FAIL, stay in the bootloader and serve every channel.

The one hop that changes everything

Today the board holds the signing key's public half directly, so rotating that key means physically re-flashing every board. A delegation chain inserts one verification step — and that single hop is the whole difference between the two designs.

Status

Both secrets are still placeholders

fw_signing_key.TEST_ONLY.pem is committed to a public repo, so anyone can produce a signature the current fw_pubkey.c accepts. iap_fixed_password.txt still reads IAP-FIXED-PASSWORD-TEST-ONLY-CHANGE-ME. Both are fine on the bench and neither is acceptable on a board that leaves the desk.

Note also that shipping the signing key inside the Arduino package makes it effectively public by design — users compile their own PLC programs. The signature then guards against corrupted images and remote injection, not against the person holding the board.
