# 需求框架

**这个产品要做到什么，以及每一条做到没有。** 建于 2026-08-17。

配套的 [TEST-PLAN.md](TEST-PLAN.md) 回答"怎么证明"；这里只回答"要什么"和"到哪一步了"。

## 怎么读

每条需求都写成**可判定**的一句话 —— 能回答"是/否"的才算需求，"提高可靠性"不算。

| 状态 | 含义 |
|---|---|
| ✅ | 已实现**且**有实测证据。证据在 [../IAP-STATUS.md](../IAP-STATUS.md) |
| 🟡 | 已实现，但**没有测试能证明**它（或只测过一半） |
| 🔨 | 在做 / 已立项，设计在 [Todo/](Todo/) |
| ⬜ | 未做，未立项 |
| ⛔ | 明确不做，理由在 [../DEFERRED-DESIGNS.md](../DEFERRED-DESIGNS.md) 或本表备注 |

「验证」列填测试用例编号（定义在 [TEST-PLAN.md](TEST-PLAN.md)），或者「手工」「无」。

> ⚠️ **🟡 才是这张表最有用的部分。** ✅ 和 ⬜ 都不会骗人，🟡 会 —— 功能在跑，没人测，改坏了也没人知道。

## A · 升级通道

板子必须能被升级，且升级的入口不止一条 —— 唯一一条入口坏掉就等于变砖。

| ID | 需求 | 状态 | 验证 | 备注 |
|---|---|---|---|---|
| **A1** | 通过 USB CDC 能把一个 app 镜像烧进板子并正常启动 | ✅ | 手工 | 含"板上无有效 app"和"app 在跑 → 1200 touch → 交权"两条路径 |
| **A2** | 通过以太网能烧写**停在 bootloader** 的板子 | ✅ | 手工 + T3 | UDP 发现 → getpubkey → TCP 传输 |
| **A3** | 通过以太网能烧写**正在跑 app** 的板子（先认证 reboot） | ✅ | 手工 | 认证 reboot → 广播发现 + UID 匹配 → TCP |
| **A4** | 按住 BOOT0 复位能强制进入上传模式 | ✅ | 手工 | 日志 `** UPLOAD Mod ... (BOOT0 held)` |
| **A5** | 从 CDC 请求进入上传模式时**不启动**以太网 | ✅ | 手工 | 通道隔离，**是设计不是故障** |
| **A6** | app 请求进上传模式的通道只有一条（SRAM4 `boot_handoff_t`） | ✅ | P2 静态 | 跨仓镜像，布局已自动比对 |
| **A7** | 同一台主机上的多个工具不会互相打断上传 | ✅ | 手工 | 上传锁；文件名和过期时间已自动比对 |

## C · 完整性与信任

**这一组决定"什么代码可以在这块板子上跑"。** 每一条挂的都是能不能出货。

| ID | 需求 | 状态 | 验证 | 备注 |
|---|---|---|---|---|
| **C1** | 镜像先过 CRC32 | ✅ | 手工 | |
| **C2** | 镜像的 SHA-256 + ECDSA 签名在**上传时**被校验 | ✅ | **S1 S2** | 两种失败分开测：S1 是"没有任何密钥能产生的签名"，S2 是"格式完全正确但签方不对" |
| **C3** | app 的签名在**每次启动时**被重新校验 | ✅ | **S3**（S1 只是副产品） | 现算哈希再验签，不读存下来的副本。⚠️ SDRAM staging 之后 **S1 已经证明不了这条** —— 失败的上传根本不碰 app 区。S3 是直接改坏已装好的 app |
| **C4** | **校验失败的上传不破坏已装好的 app** | ✅ | **G1** | ★ SDRAM staging 存在的全部理由。2026-08-17 实测 |
| **C5** | 会话认证：HMAC 挑战应答，nonce 跨掉电不重复 | ✅ | **H1 + H2 + AU1** | 2026-08-17 实测：真断电（`Reset cause: POR`）后计数器 69→71 未归零，16 个 nonce 全不同。H2 同日首次真跑（此前一直 SKIP，**而且早就编不过了**），11 条断言全过 |
| **C6** | 降级（装更旧的版本）会被拦下 | ✅ | **DG1** | ⚠️ **纯工具侧策略**。bootloader 只在 `getversion` 报出已装版本（`IAPServer/IAP_server.c:191`），`expected_version` 存进 metadata 但**从不比较**（`:352`）—— 改过的工具照样能降级 |
| **C7** | 签名密钥能整体轮换（三处副本同步） | 🟡 | **P2** | 三份密码副本已自动比对；轮换后**必须 ST-Link 重烧 bootloader** |
| **C8** | 工具在传输前就能判断"这块板收不收我的签名" | ✅ | **K1–K6** | 六种情况全部自动化 |
| **C9** | 签名的编码在签方和验方之间一致 | ✅ | **X1 X2** | 独立第三实现交叉验证 |
| **C10** | 板子有办法脱离"出厂公开根"，且不需要 ST-Link | 🔨 | 无 | **6 步里第 1、2 步已做**（2026-08-17：flash 尾部 8K 预留 + 只读扫描，实测三种记录状态）。⚠️ **现在仍然永远用默认根** —— 验签是第 5 步，采信没验签的记录比没有这功能更糟。⛔ 第 6 步卡在"恢复出厂怎么触发"未定，BOOT0 长按已被上传模式占用。见 [Todo/M1-owner-slot.md](Todo/M1-owner-slot.md) |
| **C11** | 板子从第一版就懂证书链，简单模式走同一条验证路径 | 🔨 | 无 | [Todo/M2-cert-chain.md](Todo/M2-cert-chain.md) |
| **C12** | 撤销叶子证书，且**永不能撤到一个有效根都不剩** | ⬜ | 无 | 依赖 C11。ESP32 aggressive revoke 是反面教材 |
| **C13** | 产线给每块板发唯一密钥，取代固定密码 | ⛔ | 无 | 见 [../DEFERRED-DESIGNS.md](../DEFERRED-DESIGNS.md) |
| **C14** | flash 写保护（WRP）禁止 app 写 bootloader 区 | ⛔ | 无 | 当前工程未使用；是堵住出厂状态那个洞的唯一手段 |

> ⚠️ **C10–C12 之前，出厂板必然不设防** —— 默认根私钥公开是产品定位的直接推论，不是妥协。完整推理在 [../OWNERSHIP.md](../OWNERSHIP.md)。
