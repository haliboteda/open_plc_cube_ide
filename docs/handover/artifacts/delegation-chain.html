The Delegation Chain

Today the board holds the signing key's public half, so rotating that key means physically re-flashing every board. Insert one verification step and the board holds a root instead — a root that never has to change. Fixed-length structures only: no X.509, no ASN.1 parser.

One root, two jobs

The same root that decides which firmware may run can also decide who may open an update session. A capability field in each leaf keeps the two authorities separate, so an operator credential can never sign firmware.

The certificate is a struct, not a document

160 bytes at fixed offsets. Every field is read with a load instruction, not a parser. This is the single most important design decision here: attacker-supplied ASN.1 in front of a bootloader with no MMU and no heap protection is exactly the kind of code that produces memory-safety CVEs. 

/* fw_cert.h -- fixed offsets, no parser */
#define CERT_SIZE         160U
#define CERT_MAGIC        0x434C504FU   /* 'OPLC' */
#define CERT_SIGNED_LEN    96U          /* everything but the signature */
#define CAP_SIGN_FIRMWARE 0x00000001U
#define CAP_OPEN_SESSION  0x00000002U
#define CAP_REVOKE        0x00000004U

/* Returns the root index that vouched for this leaf, or -1. The caller needs
 * the index so a revoke command can be refused when it targets its own root. */
static int cert_verify(const uint8_t c[CERT_SIZE], uint32_t need_caps)
{
    uint8_t h[32], uid[12];
    int i;

    if (rd32(c + 0) != CERT_MAGIC)                     return -1;
    if (rd32(c + 4) != 1U)                             return -1;
    if (rd32(c + 8) < bootloader_state_min_serial())   return -1;
    if ((rd32(c + 12) & need_caps) != need_caps)       return -1;

    /* All-zero device_uid means "any board". */
    iap_keyderive_get_machine_id(uid);
    if (!is_zero(c + 16, 12U) && memcmp(c + 16, uid, 12U) != 0) return -1;

    sha256(c, CERT_SIGNED_LEN, h);
    for (i = 0; i < ROOT_COUNT; i++) {
        if (bootloader_state_root_disabled(i)) continue;
        if (uECC_verify(root_public_keys[i], h, 32U, c + 96, uECC_secp256r1()))
            return i;
    }
    return -1;
}

Two roots, and either can disable the other. A single root is a single point of total product-line failure. The spare costs 64 bytes of flash, and the root_disabled bitmask — one journal record, raised only by a CAP_REVOKE leaf that chains to a different root — turns a leaked root from "re-flash every board" into a command you can push over the network. Without that rule a stolen root could disable the honest one and lock you out, so the check is not optional.

What a boot actually does

Who holds what

Three machines, and only one of them ever sees the root private key. The machine that builds the bootloader does not need it, and neither does the machine that builds sketches — which is what makes a split setup work without couriering secrets around.

The three commands

Only the first one needs the offline machine, and it runs once per customer — not per build, not per release.

  1. Vendor, once: create the roots rotate_keys.sh --new-root on the offline machine. Writes root_key.pem, root_key_backup.pem and keys/root_pubkey.inc. Build the bootloader with that .inc, flash boards at manufacturing, then take the two .pem files offline for good.
  2. Vendor, per customer: issue a leaf IAPTool issue --root=root_key.pem --caps=firmware,session --out=customer_a, optionally --uid=<12-byte hex> to bind it to one board. Produces customer_a.pem and customer_a.cert. Ship both to that customer's <IAPTool>/keys/.
  3. Customer, every day: nothing changes IAPTool cdc app.bin COM5 — exactly the command they run today. The tool finds keys/leaf_key.pem and keys/leaf.cert by the same rules it already uses for the signing key, signs the image and the challenge, and sends the certificate along. No new flags, no new steps.

When a key is lost

Losing a key and leaking a key need different answers, and the chain is what makes most of these recoverable at all. Today every row below reads "re-flash every board".

What happenedImmediate effectRecovery
Customer loses their leaf key They cannot sign or flash. Boards keep running. Issue a replacement leaf with a higher serial. No board is touched.
Customer's leaf key leaks Whoever has it can flash boards that accept that leaf. Issue a replacement, push a revoke raising min_serial. Boards that take the update stop accepting the old leaf.
Primary root lost None — existing leaves keep working. Issue from the backup root. Every board already trusts both.
Primary root leaked The holder can mint leaves for any board. Push revoke_root 0 signed by a backup-root leaf. Boards that take it stop trusting the leaked root.
Both roots lost None immediately — existing leaves keep working indefinitely. No new leaves can ever be issued. Recovering means re-flashing bootloaders over ST-Link.
Both roots leaked Total loss of firmware trust. New roots, new bootloader, ST-Link on every board. This is the disaster the offline rule exists to prevent.

Revocation only reaches boards that get updated

Every recovery above works by pushing a record to a board. A board that is never connected again keeps trusting whatever it last accepted. That is inherent to offline revocation with no clock and no server, not a gap in this design — but it means "revoked" should be read as "revoked on every board you can still reach".

The metadata record is the one structural change with a real cost: it currently occupies exactly one 128-byte slot, and a 160-byte certificate does not fit. Raising the slot to 512 bytes keeps the record a single slot and drops journal capacity to 256 entries — still far more than a device will see, and a reclaim already preserves the current metadata.

The extra verify is measurable but happens once per boot on a path that already does one. The authMsg[220] buffer in IAP_server.c has to grow with the command.

Revocation, without a clock

Each leaf carries a monotonic serial. The board stores a minimum acceptable serial and refuses anything below it. That is the whole mechanism.

  1. Default is zeroNothing is revoked on a fresh board, so provisioning needs no extra step.
  2. Raised by an explicit authenticated commandA new journal record type holds the minimum; a revoke <serial> command signed by a leaf carrying CAP_REVOKE appends it. Never raised as a side effect of an ordinary update, or a rollback would silently revoke itself.
  3. Checked before the signatureSerial rejection short-circuits cert_verify, so a revoked leaf costs no ECDSA work.
  4. Compromised leaf, bounded blast radiusIssue a replacement with a higher serial, push it once, and every board that takes the update stops accepting the old one. Boards never updated stay exposed — an inherent limit of offline revocation, worth stating plainly rather than papering over.

Migration

A hard cutover, not a compatibility period. Supporting both formats would mean two trust paths live in the bootloader at once, and the weaker one sets the security level.

  1. Generate the root pair (and the spare)Extend rotate_keys.sh: it already generates keys, distributes copies, backs up and rolls back. It gains a root mode and a leaf-issuing mode.
  2. Build the new bootloaderkeys/root_pubkey.inc replaces fw_pubkey.inc and is #included the same way, so the file plumbing built in this round carries over untouched.
  3. Flash it over ST-LinkUnavoidable and one-time. This is the last rotation that ever needs it — which is the entire point.
  4. Ship IAPTool and the leaf togetherThe tool sends the certificate with every command. Old tool against new board fails cleanly at the first flash; they are released as a pair.

Decide this before writing any code

The root private key must survive the product, and it must not ship in the Arduino package — otherwise the chain buys revocation and easy rotation but not trust, because anyone with the package could issue their own leaf. The leaf is what ships; the root stays offline. That one rule is what every recovery path in this document depends on.

It also decides how much the chain actually buys you. Ship one leaf with the public package and you are close to where you are today — better rotation, but a credential everyone shares. Issue per-customer leaves and a leak becomes one revocation instead of a product-wide event. The mechanism supports both; the operational choice is yours and it is the one that sets the security level.
