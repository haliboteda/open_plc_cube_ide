# 测试框架

**怎么证明 [REQUIREMENTS.md](REQUIREMENTS.md) 里的每一条。** 建于 2026-08-17。

## 三条原则（沿用 [../BUILD-AND-TEST.md](../BUILD-AND-TEST.md)）

1. **测真实代码路径。** 需要"传输进行中"的用例把 IAPTool 当子进程拉起来跑真实烧写，不自己实现传输。
   > 教训：手写的探测脚本能正常读到设备，掩盖了 IAPTool 自己的真 bug，直到用真实工具跑完整流程才暴露。**一次性脚本测的是它自己的逻辑。**
2. **加密逻辑 import，不重写。** 负向用例只把该错的那一处弄错，其余全用出货代码。
3. **反向用例和正向用例一样重要** —— "不该发生的事没发生"最容易漏，而且只在现场暴露。

## 四层，由快到慢

**前一层不过就不要往下走。** 上板调试的每一轮都比主机测试贵一个数量级。

| 层 | 跑什么 | 要板子 | 耗时 | 一条命令 |
|---|---|---|---|---|
| **0 静态** | P1–P3 | 否 | 秒 | `tools\selfcheck.ps1` 的一部分 |
| **1 主机** | H1 H2 K1–K6 X1 X2 | 否 | 约 2 分钟 | **`tools\selfcheck.ps1`** |
| **2 构建烧写** | T0 + 尺寸门禁 | 是 | 分钟 | `tools\flash-bootloader.ps1` |

| **4 人工** | S4a S4b M3 O1 | 是 + 人 | — | 见下面各条 |

用例的**判据和运行方法**在 `$TOOL/TestTool/TEST-CASES.md`（贴着代码走，跨仓不搬）。这份文档管**覆盖矩阵**、**待补用例的完整设计**和**最近结果**。

> ### ★ H2 的 SKIP 掩盖了一处真实损坏（2026-08-17）
>
> H2 长期报 SKIP（本机没有 host C 编译器）。装上 MinGW-w64 之后第一次真跑，**它根本编不过**：
>
> ```
> iap_auth.c:139: error: 'RTC_BKP_DR3' undeclared
> ```
>
> 原因是 2026-08-17 修 DR2 撞车时把 VBAT witness 从 `DR2` 搬到了 `DR3`，而 `host/bootloader_unit/stubs/rtc.h` 只定义到 `DR2`，**没人跟着改**。
>
> **也就是说 H2 从那次修复起就是坏的，而 SKIP 让它看起来只是"没测"。** 文档里原来写的是"静默跳过的检查会被读成通过，那比没有这个检查更糟" —— 实际情况比这还糟一层：**它掩盖的不是覆盖缺失，是这个检查本身已经不能运行了。**
>
> 已修（stub 补齐 `DR0`–`DR7`，`s_bkp[8]` 本来就撑得住），11 条断言全过。
>
> **教训：一个长期 SKIP 的检查，要当成"状态未知"，不能当成"缺一个环境就能补上"。** 环境补上那天可能会发现它早就烂了。

下面每条按同一骨架写全，落地时照抄即可。**没写实际结果的就是没跑过**，不要填"应该没问题"。

### S2 · 密钥不匹配 ✅ 2026-08-17 已实现并通过

| | |
|---|---|
| **目的** | 分开验证"签名坏了"和"签名是别人签的"。两者现象都是"拒绝启动" |
| **覆盖需求** | C2 |
| **前置条件** | 设备停在 bootloader；手上有一把**和板子里公钥不配**的私钥 |
| **步骤** | 1. 用不匹配的私钥签一个结构完整的镜像<br>2. 绕过 IAPTool 的 `getpubkey` 预检直接送上去（做法同 S1）<br>3. 复位 |
| **预期** | 上传阶段回 `Signature Failed`；复位后旧 app 照常启动（app 区未被碰） |
| **验证方式** | `TestTool S2 --ip=… --bin=… --password-file=…`（`TestTool/signature_wrongkey.go`） |
| **实际结果** | **2026-08-17 通过**。板子回 `Signature Failed`；复位后 `** APP Mod ...` + `UART echo ready` 正常。journal 88→89 槽，说明拒绝这件事被记了事件 |
| **结论** | ✅ |

> **为什么必须和 S1 分开**：混在一起测过一次，结果把一次密钥轮换误判成校验代码的 bug。

**落地时的两个决定：**

| 决定 | 理由 |
|---|---|
| **签名由 `IAPTool sign` 子进程真实生成**，不在用例里自己签 | 和"传输不自己实现"同一条原则。自己签等于顺带在测本用例对 `r‖s` 编码的理解，而那是 X1/X2 的活 |
| **上传前先 `getpubkey`，确认板子信的不是这把临时密钥** | 临时密钥是每次现生成的，撞上是不可能事件。这道闸防的是**将来有人把它改成固定密钥文件** —— 那样用例不会失败，它会**真的把板子刷了** |

### S3 · 启动期签名失败（纯）✅ 2026-08-17 已实现并通过

| | |
|---|---|
| **目的** | 只走启动校验这一条路径 |
| **覆盖需求** | **C3** |
| **前置条件** | 板上有一个**已经正常启动过**的 app；有 ST-Link；**手上有一个已签名的 app 镜像用来恢复** |
| **步骤** | 1. **先证明恢复路径通**（烧一次，看着它起来）<br>2. 用 ST-Link 把 app 区中间的一个字节改掉<br>3. 复位<br>4. 重烧恢复 |
| **预期** | `metadata present` + `App signature invalid or absent`，**且没有** `** APP Mod`<br>重烧即可恢复 |
| **验证方式** | `tools\run-s3.ps1 -Bin <app.bin>`，含恢复 |
| **实际结果** | **2026-08-17 通过**。第 41858/83716 字节 `0x12`→`0xED`；复位后 `metadata present` + `App signature invalid or absent - staying in bootloader` + `UPLOAD Mod ... (no valid application)`，**没有 `APP Mod`**；重烧后 `Checksum and signature OK` → `** APP Mod ...` 恢复 |
| **结论** | ✅ C3 现在由 S3 直接证明 |

> ⚠️ **原来写的预期是错的，已改。** 原文说"**不是** `no valid application`（后者说明 metadata 也没了）"。实际上 `App signature invalid or absent` 和 `no valid application` **出自 `server_decide()` 的同一个分支**（`IAPServer/IAP_server.c:482-494`），必然同时出现。真正区分"app 坏了"和"metadata 也没了"的是 `Bootloader state:` 那行里的 **`metadata present` / `absent`**（`bootloader_state.c:155`）—— [../JOURNAL.md](../JOURNAL.md) 的表格一直是对的，是这里抄错了。

**为什么 S1 不能代替 S3**：SDRAM staging 之后，失败的上传**根本不碰 app 区**（就是 G1 那条）。所以 S1 的"下次启动被拒"那一半现在只发生在 metadata 和 app 不匹配的情况下，**证明不了"已装好的 app 每次启动都被重新校验"**。S3 是唯一直接测这条的。

**落地时的三个决定：**

| 决定 | 理由 |
|---|---|
| **改一个字节，不是擦掉整块** | 擦掉只能证明"发现 app 没了"。改中间一个字节才证明**哈希真的覆盖内容** |
| **先擦整个扇区再把改过的完整镜像写回**，而不是直接改那一个字节 | ⚠️ STM32H7 的 flash 每 256 位带 ECC，**同一个字编程两次**会让存下来的 ECC 变成两次的按位与，读出来就是不可纠正错误并把 CPU 打进 fault。那样 bootloader 会在算哈希时崩掉，而不是干净地报签名不过 —— 另一种失败，而且很难看懂 |
| **恢复路径先证明，再破坏** | 顺序反了的话，万一恢复镜像本身有问题，板子起不来而手上没有任何已知可用的东西 |

### AU1 · 板上 nonce 跨掉电不重复 ✅ 2026-08-17 已实现并通过

| | |
|---|---|
| **目的** | 重放保护靠的是 nonce **唯一**（不是不可预测）。计数器存在 RTC 备份寄存器里，靠 VBAT 保持 |
| **覆盖需求** | **C5** |
| **前置条件** | 设备可发起 `authchallenge`；VBAT 电池在位 |
| **步骤** | 1. 连发 N 次 `authchallenge`，记下每个 nonce<br>2. 断电、重新上电<br>3. 再发 N 次，记下 nonce<br>4. 检查 2N 个 nonce 的前 4 字节（计数器部分）**严格递增且无重复** |
| **预期** | 无重复；掉电后接在旧序列上继续，不归零 |
| **验证方式** | `TestTool/tools/run-au1.ps1`（编排 + 人工断电），用例本体 `TestTool/nonce_replay.go` |
| **实际结果** | **2026-08-17 通过**。断电前 counter 62→69，上电日志 `Reset cause: POR`（**确认是真断电不是复位**），断电后 71→78。16 个 nonce 全不同，UID 字 0 两阶段一致 |
| **结论** | ✅ C5 从 🟡 转 ✅ |
| **为什么值得做** | 2026-08-17 刚发现过一个真实缺陷：bootloader 的 witness 和 app 的计数器都占 `DR2`，**每次经过 bootloader，app 就重复发放同一批 nonce**。这个用例能直接抓到那类问题，而当时是靠肉眼看日志发现的 |

**跨掉电的 69→71 那个 gap 是对的**：中间那两次 challenge 是 `enter-bootloader` 自己的认证 reboot 消耗的。用例断言的是**严格递增**，不是"恰好加一"（阶段**内**才要求恰好加一）。

**编排上的三个决定：**

| 决定 | 理由 |
|---|---|
| **必须真断电，不能按复位** | 复位根本不碰备份域。只做复位的话，**一块 VBAT 电池已经没电的板子照样能通过** —— 而那正是这个用例要抓的板子 |
| **不让人按回车确认，而是看板子的 UDP 发现应答判断断电真的发生了** | 人的确认可以撒谎（也可以看错提示）。连续三次探测无应答才算断电，单次丢包不算 |
| **两路独立核对**：nonce 里的计数器 vs bootloader 自报的 `nonce counter = N` | 前者是从 nonce 前四字节推出来的，后者是直接读备份寄存器。两者对不上，说明其中一个不是在读它声称的东西 |

⚠️ **`nonce counter = N` 这行只在 bootloader 停下来的时候才打。** 板上有有效 app 时，上电那次会直接交权给 app，**根本走不到那句**。2026-08-17 首次跑的时候脚本只翻上电日志，于是报"cross-check not available"，而那个数字其实就在紧接着的 `enter-bootloader` 日志里（69，和断电前最后一个 nonce 完全一致）。已修：两份日志一起翻。

⚠️ **PowerShell 5.1 的坑，同一处**：`enter-bootloader.ps1` 全部用 `Write-Host` 输出，那是**信息流（6）不是成功流**。`2>&1 | Out-String` 抓到的是**空字符串**，而文字照样出现在控制台上 —— 看起来像板子没打印。必须用 `6>&1`。

### DG1 · 降级被拦下 ✅ 2026-08-17 已实现并通过

| | |
|---|---|
| **目的** | `--downgrade=refuse` 时装不进更旧的版本 |
| **覆盖需求** | **C6** |
| **前置条件** | 板上装着版本 X 的 app（由 `fake_board.py --fwver` 提供） |
| **步骤** | 1. 准备一个版本 < X 的镜像<br>2. `IAPTool ether ... --downgrade=refuse`<br>3. 再用 `--downgrade=allow` 跑一次 |
| **预期** | 第一次被拒且**板上的 app 不受影响**；第二次成功 |
| **验证方式** | `$TOOL/TestTool/host/fakeboard/run-downgrade.ps1`，**不需要真板子**；selfcheck 步骤 **A12** |
| **实际结果** | **2026-08-17 五个用例全过**：`refuse-older` / `allow-older` / `ask-no-console` / `same-version` / `newer` |
| **结论** | ✅ C6 从 🟡 转 ✅ |

**落地时比原设计多做的三件事**（都不是凑数）：

| 加了什么 | 为什么 |
|---|---|
| **每条都断言"板子有没有收到 `flash` 命令"**，不只看工具打了什么 | 一个打印了 `Downgrade refused` 之后照样上传的工具，能轻松骗过只看日志的检查。**C6 的真正主张是"板上的 app 没被碰"，只有板子那侧的日志能证明**。正向用例还要求 `IMAGE FULLY RECEIVED` —— 发出 `flash` 只说明闸门放行了，不说明传输活到最后 |
| **`same-version` 边界用例** | 比较是 `local >= remote`（`auth.go:248`）。这里差一位就会**禁止重刷同一个版本**，而那是所有人最常做的事 |
| **`ask-no-console` 强制喂管道 stdin** | `--downgrade=ask` 的行为取决于 stdin 是不是控制台。那条分支存在的原因是：从 IDE 启动时读 stdin 立刻返回 EOF，**以前会被报成"操作员拒绝"，而根本没人被问过**。不强制管道的话，这条用例的结果取决于脚本是怎么被启动的 |

> ⚠️ **DG1 覆盖的是工具侧的全部，而工具侧就是 C6 的全部。** bootloader 只在 `getversion` 报出已装版本，`expected_version` 存进 metadata 但从不比较 —— **换一个改过的工具照样能降级**。这不是缺陷，是 C6 当初就这么定的范围，写在这里是为了别让人以为板子在把关。

### 过期的结论是一类没人在测的缺陷

2026-08-17 收尾时核对 `../../RELEASE-NOTES.md`，**四条 known-issue 里有四条已经不对**：

| 它写的 | 实际 |
|---|---|
| bootloader 报版本 `0.1.2` | 当天已改成 `0.1.3` |
| `[BOOT]` banner **到不了** RS232 端子 | 到得了 —— 靠电荷泵余电，`millis=12` 实测 |
| 乱码字节"三个候选，都未确认" | 已排除两个，根因确定是电荷泵塌陷 |
| 备份域误报"根因仍未查明" | 当天已定位（DR2 跨仓撞车）并修复 |

**这份是对外的，升级风险全靠它兜着。** 一条过期的 known-issue 会让读的人去查一个已经不存在的问题，比没有这一条更糟。

`P1` 只能抓住**版本号形态**的过期（它就是这么发现第一条的）。其余三条是靠人工逐条核对翻出来的，**没有任何自动化能覆盖**。
