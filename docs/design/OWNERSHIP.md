# 所有权与信任根

**状态：✅ 已实现并实测（2026-08-18）。** 配图版是 [../archive/artifacts/owner-slot.html](../archive/artifacts/owner-slot.html)（⚠️ 快照，和本文打架时以本文为准）。

**本文件是设计推理的出处**。

出货工具的入口：`IAPTool getowner / takeown / setowner`，用法见 `$TOOL/README.md`。TestCase 的 `run_takeown.py` / `run_setowner.py` 仍然是用例侧的驱动。

机制上和 [JOURNAL.md](JOURNAL.md) 独立，但两者都住在 bootloader 独占的 flash 区域里，改任何一边之前先读另一边。

## 一切的起点：出厂默认根的私钥必然是公开的

1. 客户下载 Arduino 包，**写自己的 PLC 程序**并上传
2. 上传要签名 → 签名要私钥 → 私钥得在客户机器上
3. 项目开源，不给客户发任何专属材料
4. ⇒ **那把私钥必须在开源仓库里 ⇒ 公开**

反过来假设：如果出厂根私钥是厂商的秘密，客户就只能跑官方签的固件、不能跑自己的 sketch —— 产品没了。

> **⚠️ 所以出厂状态必然不设防。这不是妥协，是产品定位的直接推论。**
> `IAPServer/keys/README.md` 里那条「anyone who cloned the project can sign an image」不会因为上证书而改变。

真正要设计的只剩两件事：客户**知不知道**自己不设防；客户想加固时**有没有一条不用 ST-Link 的路**。

## 双模式：简单（A+）与升级（B）

板子**从第一版就懂证书链**，工具默认发**自签证书**（叶 = 根，K 给自己作证）。用户体验等同单密钥；要切授权链时一条命令，**板子一个字节都不用改**。

让"一条命令"成立的三个机制，缺一条就不成立：

1. **板子里的公钥从一开始就当「根」看**，不是当「固件签名者」看 —— 升级时 K 原地升格为根，它没变，所以板子不用动
2. **简单模式也走验证书的路径**，只是那张证书自签。板子的检查恒为「这张纸的章，是我认的根能核对的吗」，**没有自签特例分支**
3. 工具**每次上传都把证书一起发**

第 2 条是全部价值：简单模式不是"绕过验证"，而是"验一张恰好自签的证书"，所以**不存在高级分支没人走、悄悄烂掉**。

**代价要有意识地买**：简单模式那张自签证书在安全上不增加任何东西，纯粹是 160 字节 + 一次验签，唯一作用是保住升级通道。

## owner 记录区：寄生在 bootloader 扇区尾部

### 为什么是这里

H743 的擦除粒度是**整个 128K 扇区**，没有更小的。所以任何"独立生命周期"的 flash 区域最少要 128K —— 除非它寄生在一个已经被占用、但没用满的扇区里。

| 候选 | 结论 |
|---|---|
| 现有 state 扇区 | ❌ `journal_reclaim()` 整扇区擦。搬运再写回的话掉电窗口 = 擦除耗时，丢了就**静默**退回默认根 |
| 新开专用扇区 | 可行但白付 128K，还要绕开下面那个常量陷阱 |
| **bootloader 扇区尾部** | ✅ **净增 0 扇区** |

关键性质：**只追加，永不擦除**。ST-Link 烧 bootloader 时整扇区被擦过一次，镜像之后的字节全是 `0xFF` —— 正好是一片可追加的空地。

### 尺寸

扇区 131,072 B，链接器只拿到 120K（122,880 B），尾部 8K 留给 owner 记录。**镜像当前多大、余量多少 → `$PROD/docs/STATUS.md` 的 E3 行**（唯一出处，这里不拄一份）。

| 保留 | `FLASH LENGTH` | owner 区起点 | 镜像余量 | 可存记录 |
|---|---|---|---|---|
| 4K | 124K | `0x0801F000` | 30,588 B | 25 条 |
| **8K（建议）** | **120K** | **`0x0801E000`** | **26,492 B** | **51 条** |
| 16K | 112K | `0x0801C000` | 18,300 B | 102 条 |

⚠️ 要改 `STM32H743IIKX_FLASH.ld` 的 `FLASH LENGTH` 128K → 120K，否则链接器会把代码放进这 8K。这一行已经在 `$PROD/docs/CONVENTIONS.md` 的「重新生成后须复查」清单里，**是个已知易失守的点**；`.ld` 里那段解释"为什么写 128K 不写 2048K"的注释要一起更新。

### ⚠️ 这条路恰好绕开了 `RESERVED_TAIL_SECTORS` 那个地雷

owner 区寄生在 bootloader 已占的扇区里，**根本不加尾部扇区**，所以碰不到它。⚠️ 但真要加尾部扇区的人得知道：**三处地址守卫全锚在 `IAP_STATE_SECTOR_ADDR` 上，一个都不看 `RESERVED_TAIL_SECTORS`** —— 改那个常量保护不了任何东西，只会静默弄坏 reclaim，而且不会编译报错。

## 状态机

```
上电 → 扫 owner 记录区
        │
        ├─ 空，或最新一条是 cleared ──► 用编译进来的默认根 R0
        │                                ⚠️ 不设防，每次启动都要告警
        │
        └─ 有有效记录 ────────────────► 沿链取最后一条有效的作为根
        │
        ▼
   ① 用这把根验证书  ② 用证书里的叶公钥验镜像
   （两条路之后完全相同，验证代码只有一份）
```

### 告警的触发条件是「用的是那把公开根」，不是「槽空」

**2026-08-16 决定。** 编译期的那把根**是不是公开的，取决于谁编译了 bootloader**：

| 谁编译 | 编译进去的根 | 私钥 | 开箱状态 |
|---|---|---|---|
| 厂商（出厂烧录） | 仓库里那把 | **公开** | 🔴 不设防 |
| 客户自己编译（跑 `rotate_keys.sh` 换掉 `keys/fw_pubkey.inc`） | 他自己的 | 保密 | 🟢 **开箱就安全** |

所以「owner 槽空 → 每次启动告警」这个规则**对自己编译的客户是纯误报** —— 他的板子明明安全，却一直被告知"任何人都能刷写"。**会训练用户忽略这行告警，规则就废了。**

**做法：bootloader 里存一份公开根的 SHA-256，启动时比对当前信任的根。只有相等才告警。**

| 情况 | 当前根 vs 公开根 | 告警？ |
|---|---|---|
| 出厂状态 | 相等 | ✅ 告警 |
| 客户自己编译换了根 | 不等 | 不告警 |
| 出厂板 takeown 之后 | 不等 | 不告警 |

代价：32 字节常量 + 启动时一次 64 字节的哈希比对。**零配置，三种情况自动都对。**

⚠️ 判断依据是"我信任的这把根，是不是那把全世界都有私钥的"—— 这才是要告警的**真实条件**，"槽空不空"只是个会出错的代理指标。

### 客户自己建根之后，他的密钥怎么和根挂上

**他不需要额外建根 —— 第一次 `rotate_keys.sh` 生成的那把就是他的根**，简单模式下他只是同时也用它直接签固件。"升级到授权链"不是建新根，而是**停止用根直接签，改用根签发的叶子来签**。

**绑定关系只有一样东西：根私钥对证书的签名。** 没有目录、没有注册表、没有名字匹配。

```
简单模式（K 给自己作证）              授权链（K 签 L）
板子里: K_pub                        板子里: K_pub  ← 一个字节没变
   │ 验证书签名                          │ 验证书签名
   ▼                                     ▼
cert{ pubkey=K_pub, sig=K签 }        cert{ pubkey=L_pub, sig=K签 }
   │ 取出 K_pub                          │ 取出 L_pub
   ▼                                     ▼
镜像签名 = K 签                       镜像签名 = L 签
```

板子的代码两种情况**完全一样**，它只问"这张纸是 K 签的吗"。纸上写的公钥是不是 K 自己，板子不关心。

⚠️ 升级之后那张自签证书**仍然有效**（它还是 K 签的），所以**根依然可以直接签固件**。这不是缺陷 —— 根持有者本来就是最终权威 —— 但别指望"升级后根就不能直接签了"。

### 这和 UEFI Secure Boot 是同构的

独立推出来的，事后才发现撞上了 —— **建议直接借用 UEFI 的术语写文档**，读者有现成心智模型。

| 这里 | UEFI |
|---|---|
| owner 区为空 → 默认根 R0 | **Setup Mode**（没有 Platform Key，谁都能写） |
| G1 认领 | 写入 PK → 进 **User Mode** |
| 换 owner 必须被当前 owner 签名 | 改 PK 必须被 PK 签名 |
| 追加 cleared 记录，物理门控 | 删除 PK 回 Setup Mode，需进固件设置界面 |

## 三个操作

**都不擦除** —— 这个扇区里还住着 bootloader 自己。

| | 操作 | 对记录区做什么 |
|---|---|---|
| ① | 认领 `takeown` | 往空区追加 G1。**没有前任可以签它 = TOFU** |
| ② | 换 owner | 追加 G3，**必须被 G2 签名**，否则 bootloader 忽略 |
| ③ | 恢复出厂 | 追加一条 `cleared` 记录。最新一条是 cleared → 回落 R0，回到 TOFU |

② 是这套东西真正安全的原因：**攻击者即使能往 flash 写字节，写出来的记录也过不了 G2 的签名校验**，bootloader 认的仍然是 G2。

### 规则

| | 内容 | 挡住 | 挡不住 |
|---|---|---|---|
| **R1** | 认领必须按住 BOOT0 | 远程顺手接管出厂板子 | 出厂状态下上传恶意 sketch 直接写这片区域 |
| **R2** | 换 owner 必须由当前 owner 根签名 | 已认领板子被夺走，**包括有 flash 写权限的代码** | — |
| **R3** | 恢复出厂必须物理动作 | 远程把别人的板子降级回公开根 | 有物理接触的人恢复出厂后接管 |
| **R4** | 撤销只针对叶子编号，**永不能撤到一个有效根都不剩** | 把自己撤成永久变砖 | — |

R3 挡不住的那条**必须接受** —— `keys/README.md` 已把"防不住手里拿板子的人"写成设计前提。反过来不给恢复出厂，客户丢了根就是永久变砖，而他恰恰没有 ST-Link。

**R4 不是假想。** ESP32 Secure Boot v2 的 aggressive revoke 是真实反面教材，Espressif 官方文档自己写着签名校验失败触发撤销时 "could also brick the device permanently if all the keys are revoked"。

## 位置表：boot 还是 app

| 东西 | 住在哪 | 谁读 | 谁写 | core 要改吗 |
|---|---|---|---|---|
| 默认根 R0 公钥 | bootloader rodata | boot | 编译期 | 不用 |
| **owner 根记录链** | `0x0801E000` boot 扇区尾部 | boot | boot | 不用 |
| 撤销状态 | 同上（也要免疫 reclaim） | boot | boot | 不用 |
| 证书 | `0x081E0000` M 记录里 | boot | boot | 不用 |
| app 镜像 | `0x08020000` 起 | boot 算哈希 | boot | 不用 |
| metadata（M 记录） | `0x081E0000` state 扇区 | boot | boot | 不用 |
| BOOT0 按键状态 | PG9 GPIO | boot | — | 不用 |

> **最后一列全是"不用"。owner 槽完全活在 bootloader 里，Arduino core 一行都不用改** —— 认领要求 BOOT0 物理按键，那时 app 根本没在跑。不涉及跨仓镜像、不用重新分发板卡包。
>
> 对比：会话认证一旦改成证书，core 侧 `iap_keyderive` 必须跟着改。**两件事成本差一个数量级，应该影响实施顺序。**

**证书为什么可以留在 journal 里**：它只需要验证*当前那个* app，而 `journal_reclaim()` 只发生在 `save_metadata()` 内部 —— 擦完立刻就有一条新 M 记录带着新证书写进去。**只有 owner 根和撤销状态需要免疫 reclaim。**

### ⚠️ 撤销状态不要放 RTC 备份域

备份寄存器看着很适合放"撤销到第几号"这种小状态 —— 掉电能活、不用擦扇区。**不要。**

备份寄存器是**三个仓库共享、且没有任何机制统一分配**的资源，而且**已经撞过一次车**。一个连"谁占了哪个"都要靠翻代码才知道的地方，不该承载安全关键状态。

**谁占了哪个、那次撞车的经过和后果，在 `$PROD/docs/design/ARCHITECTURE.md` 的寄存器分配表 —— 认领任何一个之前先看那里。**

## 记录格式（**已实现，就是这个**）

```
偏移  长度  字段            说明
  0     1   type            'O' = owner 记录，0xFF = 空
  1     1   slots           5
  2     2   format_ver      1
  4     4   generation      单调递增，最大的那条有效记录获胜
  8     4   flags           bit0 = cleared
 12    64   root_pubkey     secp256r1 X‖Y；cleared 记录里全 0
 76    64   prev_sig        上一代根对前 76 字节的签名
                            G1 和 cleared 都是全 0（靠物理动作门控）
140    20   reserved
                            160 字节 = 5 × 32 字节 flash word
```

`_Static_assert` 锁死尺寸，理由同 journal。**`format_ver` 从第一版就要有** —— 将来任何格式演进才不会变成破坏性迁移。

## 诚实的上限

> **owner 槽的安全上限 = "这块板子上能不能跑任意代码"。**

- **出厂状态：能。** 默认根私钥公开 → 谁都能签 sketch → 谁都能写 owner 区。**R1 的 BOOT0 只保护受支持的那条路，不是密码学保证**，第一次认领本质上先到先得
- **已认领之后：不能。** 跑代码要先过签名，签名要 owner 私钥。从这一刻起 R2 是真保证

**文档里要写死：板子到手第一件事是认领。**

真要堵上出厂状态那个洞，唯一手段是 **flash 选项字节写保护（WRP）—— 当前工程没有使用**。Chromebook 的等价做法是固件在交权前把"物理存在"这个能力锁死，让后来跑的软件无法声明；那背后有 TPM 硬件，这里没有。

### ⚠️ ST-Link 重烧 bootloader = 所有权重置

owner 记录和 bootloader 同扇区，重烧会一起擦掉。**语义上是对的**（能 ST-Link 的人本来就能恢复出厂），但它和「bootloader 与 app 必须捆绑升级」那条风险**叠加**：换 bootloader 的人要同时重传 app **和**重新认领。**发布说明里这两条要写在一起。**

## 借鉴与避坑（市面上的做法）

| 抄 | 来自 |
|---|---|
| Setup / User Mode 的术语和状态机 | UEFI Secure Boot |
| **每次启动常驻告警**（不是一次性提示） | Android Verified Boot：运行用户签名的系统时每次启动都提示 |
| 撤销必须保底，不能撤到没有根 | 见上面 R4 那条 |
| 物理存在由固件在交权前判定 | Chromebook：固件每次启动禁掉 TPM 物理存在命令，自定义 OS 也声明不了 |

| 避开 | 原因 |
|---|---|
| Android 的"**追加**一把根"（OEM 根 + 用户根并存） | Android 的 OEM 根私钥保密，多信任一把不掉安全性。**我们的默认根私钥是公开的，只能覆盖不能追加** |
| ESP32 的 aggressive revoke | 见上面 R4 那条 |

## 还没定

| | 影响 |
|---|---|
| 保留 4K / 8K / 16K | ✅ **定了 8K**（2026-08-17 落地） |
| 恢复出厂怎么触发 | ✅ **复位后按住 BOOT0 满 10 秒，三下继电器咔哒后松手**（2026-08-18）。不是另起一个手势，是现有 1.5 秒那次按压的自然延长 |
| 要不要上 WRP | ✅ **定了：厂商不上，留给客户自己决定要不要上**（2026-09-04）。唯一能真正禁止 app 写这片区域的手段，但设置后清除需要 ST-Link/J-Link 物理访问、重烧、重锁——不适合作为出厂默认，交给有这层防护需求的客户自己按需操作 |
| 认领时要不要绑 UID | ✅ **定了：绑**（2026-09-04）。记录里加一个 UID 字段（12 字节，从现有 160 字节格式的 20 字节 `reserved` 里划出，不用扩容、槽位数量不变），根签名覆盖这个字段；板子验证时拿自己实际的 `HAL_GetUIDw0/1/2` 比对，不一致就拒绝。堵住"把一块板的完整 owner 记录整段复制到另一块板"这条路。⚠️ **破坏性格式变更**——靠已经预留的 `format_ver` 字段处理演进，见下面「记录格式」一节 |
| 会话认证换不换成证书 | ✅ **定了：换**（2026-09-04）。板子发 nonce，工具用叶子私钥签，板子用证书里的叶公钥验——板子上从此不存任何共享密钥。直接后果：[DEFERRED-DESIGNS.md](DEFERRED-DESIGNS.md) 的"产线单板密钥"整套方案作废（C13 不用做了）；C7（密钥轮换）要解决的"三边副本怎么同步"问题一起消失；`$PROD/docs/design/ARCHITECTURE.md` 跨仓镜像表里"设备密钥派生"那一项将来可以删掉。**app 侧成本已实测**（2026-09-04，`OpenPLC_Alpha:stm32:OPEN-PLC` FQBN，STM32H743IIKx 目标）：只加 `uECC_verify()` 这一个调用，编译产物固定增加约 3.6KB（82,632→86,340 字节），额外用一份多加了约 8.3KB 无关代码的对照 sketch 验证过——这个增量不随 app 大小变化，占可用 app 空间（约 1.9MB）不到 0.2%，不构成决策障碍。测的只是签名验证库本身，不含证书解析等胶水代码，那部分预计增量更小 |
| 证书 `serial` 谁分配、怎么保证不重复 | ✅ **定了：本地计数器**（2026-09-03）。IAPCert 发证时读取根私钥旁边的计数器文件、+1、写回，4 字节 uint32，和 owner 记录的 `generation` 字段同款设计。理由：每个客户的根各自独立发号，板子只认自己那个根签的证书，不存在跨客户撞号——时间戳/随机数方案换来的"多方并发不撞号"能力，在"每个客户各自低频发证书"这个场景下用不上。⚠️ **唯一残留风险**：客户自己那台管发证书的电脑换机/重装导致计数器文件丢失，会从头计数、撞上自己之前发过的旧编号——但影响范围只限那一个客户自己的证书体系，不波及其他客户或板子 |
