# Journal 设计说明

Bootloader 用来回答一个问题的机制：**flash 里那个 app，能不能跑？**

代码在 `IAPServer/bootloader_state.{c,h}`，判定链在 `IAPServer/IAP_server.c` 的 `server_decide()`。

## 它为什么存在

Bootloader 不能靠看 app 的头几个字节猜"这像不像一个合法程序"。旧版本就是这么干的 —— 看第一个字（MSP）像不像一个合理的 RAM 地址 —— **只要 flash 里恰好有个看着像栈指针的值，损坏的或被人写进去的镜像一样能通过。**

所以每次成功烧写要留下一份**出生证明**：大小、版本、哈希、签名。下次上电拿它去核对。那份证明存在 journal 里。

⚠️ **journal 不是日志系统，是出生证明的存放处。** 事件日志只是搭便车住在同一个扇区。**所有规则都偏向保住 metadata，日志随时可以牺牲** —— 下面几条设计只有从这个前提出发才讲得通。

## 扇区布局

Flash 尾部 128KB，切成 4096 个格子，每格 32 字节（**H7 的 flash word，写入粒度下限，不能再小**）。每格第一个字节是类型。

```
扇区起点 ────────────────────────────────────────────► +128KB
┌────┬─────────────────┬────┬────┬─────────────────┬──────────────┐
│ L  │  M   M   M   M  │ L  │ L  │  M   M   M   M  │  FF FF FF …  │
└────┴─────────────────┴────┴────┴─────────────────┴──────────────┘
 1格      一条 = 4格     1格  1格    一条 = 4格        还没写过
                                          ▲               ▲
                              s_last_metadata_slot   s_next_free_slot
```

| 类型 | 字节 | 占几格 | 内容 |
|---|---|---|---|
| `M` metadata | `0x4D` | **4** | app_size / fw_version / sha256 / signature |
| `L` log | `0x4C` | **1** | event / method / peer_ip / tick_ms / auth_counter / detail / prev_hash |
| 空 | `0xFF` | — | 擦除后的 flash |

`_Static_assert` 锁死了两个结构体的尺寸。**这些尺寸就是 on-flash 格式** —— 多一个 padding 字节就会让已经写进去的每条记录的每个字段全部错位，所以让它编译失败，而不是运行时才发现。

日志的 `prev_hash` 是上一条记录原始 32 字节的 SHA-256 前 12 字节，**链式** —— 删掉或改掉中间任何一条，后面的链就对不上。截断到 96 位是为了给其他字段留空间，96 位对"能不能察觉被动过"足够。

## 上电：扫一遍账本

`bootloader_state_init()`：

```
从 slot 0 往后扫
  │
  ├─ 0xFF（空）─────► 到头了。s_next_free_slot = 此处，结束
  │
  ├─ 'L'（1格）─────► 记住哈希，i += 1，继续
  │
  ├─ 'M'（4格）─────► s_last_metadata_slot = 此处，i += 4，继续
  │                    （一路覆盖，所以最后留下的是最新那条）
  │
  └─ 其它 ──────────► 认不出，多半是旧版本布局写的
                       s_format_unknown = true，停止扫描
                       ⚠️ 账本从此只读，新事件全丢
```

**认不出就停，不猜长度往下走** —— 猜错一次就会落进别人记录的中间，之后读到的全是垃圾。

## 上电：拿它决定跳不跳

`server_decide()`：

```
crypto 自检过了吗？（sha256_selftest）
  │  否 ──► 一律当作无效。验证器本身都不可信，它的结论没有意义
  ▼
s_last_metadata_slot 有吗？
  │
  ├─ 没有 ─────────────────────────────────► app 无效
  │
  └─ 有 ──► app_size 在 (0, IAP_APP_MAX_SIZE] 吗？
             └─► 按 meta.app_size 现算 app 区的 SHA-256
                  └─► 用 meta.signature 做 ECDSA-P256 验签
                       ├─ 过 ───► app 有效 ──► 跳转进 app ✅
                       └─ 不过 ─► app 无效
                                     │
                                     ▼
                          停在 bootloader，身份报 BOOTLD-INVALID
                          （CDC + 以太网全开，等人来重传）
```

### 为什么是"验签"而不是"比对存好的哈希"

| | 只存哈希去比对 | 存签名去验证（现在） |
|---|---|---|
| 掉电半写、位翻转 | ✅ | ✅ |
| 有人重写 app 区 | ❌ **他也能把存的哈希一起改掉** | ✅ 没私钥签不出来 |

签名同时回答**完整性**（内容变了没有）和**真实性**（是不是持私钥的人签发的）。

⚠️ 但真实性这条现实里打了折：**签名私钥随 Arduino 包分发**（用户要自己编译 PLC 程序），见 `IAPServer/keys/README.md`。**它防的是损坏的镜像和远程注入，防不住手里拿着板子的人。** 这是刻意的取舍，不是疏漏。

**每次上电都验**，不是只在烧写后验一次 —— flash 会退化，也可能事后被改。

> `meta.sha256` 字段写进去了，但**全代码没有任何地方读它**。不是 bug —— 签名已经绑定了哈希，再比一次存的副本不增加安全性。将来要给工具加个核对用的命令，字段现成就在。（2026-08-16 核实）

## 写入：唯一会擦的地方

`bootloader_state_save_metadata()`，**全代码唯一的擦除点**：

```
新镜像已写进 app 区、签名已验过
  │
  ▼
剩余格子 < 4  或  s_format_unknown？
  │
  ├─ 是 ──► journal_reclaim()：整扇区擦掉，一切归零
  │         然后记一条 L: JOURNAL_RECLAIMED（detail = 丢弃的格数）
  │
  └─ 否 ──► 不擦，直接往后追加
  │
  ▼
追加 M 记录（4格）
```

**为什么只有这里能擦**：这一刻新镜像已经写进 app 区了，**旧证明描述的东西已经不存在** —— 擦掉它不损失任何有效信息。而且在这里掉电，最坏结果是"需要重刷"，**而这个结论从擦 app 区的那一刻起就已经成立了**。所以 reclaim 不引入任何新的失败模式。

换到别处擦就不成立了。

## 写日志：满了也绝不擦

`journal_log()`：

```
账本满了 或 s_format_unknown？
  ├─ 是 ──► 丢掉这条事件，计数 +1，打印一行。不擦
  └─ 否 ──► 追加 L 记录（1格），链上前一条的哈希
```

**理由**：擦一次是为了记一行日志，会连带烧掉当前有效的 metadata —— 等于**拿"app 还能不能启动"去换一行日志**。

⚠️ **代价要知道**：`s_format_unknown` 为真时，"检测到旧格式"这件事**本身也写不进日志**。要等下一次成功上传、reclaim 之后，才有一条 `JOURNAL_RECLAIMED` 留下痕迹。**事后查得到"擦过一次"，查不到"从哪次启动开始报的"。**

## 「读不到 metadata」的三种情况

现象都是"停在 bootloader"，但原因完全不同。**日志能把它们区分开，这是刻意设计的。**

| 情况 | 扫描时看到 | `s_format_unknown` | 串口现象 | 恢复 |
|---|---|---|---|---|
| **出厂空板** | slot 0 就是 `0xFF` | false | `metadata absent` | 第一次上传就正常 |
| **换了新 bootloader** | slot 0 是认不出的字节 | **true** | 多一行 `unrecognised record at slot 0` | 重传一次 app → reclaim → 恢复 |
| **上传中断 / 签名不过** | 有 `M`，但验签失败 | false | `metadata present` + `App signature invalid` | 重传 |

第二种就是 [../test/MEASUREMENTS.md](../test/MEASUREMENTS.md) 里那条捆绑升级风险：**0.1.2 的记录头是 `uint32_t type`（`'META'` = `0x4D455441`），小端存进 flash 后偏移 0 是 `0x41`；新解析器把偏移 0 当 `type` 读，`0x41` 三种都不匹配 → 在 slot 0 就干净地落进"认不出"分支。** 不会误读成新格式、也不会捡到错的 metadata —— 格式变更是可靠可检测的。

第三种的两半（上传时拒绝 / 下次启动时拒绝）是测试用例 S1 分开测的对象，别把它们合成一个。
