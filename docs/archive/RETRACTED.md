# 已被否定的结论

**这里放"当初以为是 X，后来实测否定了"。** 建于 2026-08-22，从散落在 11 个文件里的划掉文字集中过来。

**为什么留着：** 这些不是历史趣闻，是**防止重走弯路**的护栏。删掉之后，下一个人（或下一个 AI 会话）会从同样的证据出发，推出同样的错结论，再花同样的时间否定它。这件事在本项目已经发生过一次，代价记在 [../test/COVERAGE-GAPS.md](../test/COVERAGE-GAPS.md)。

**每条按同一骨架：当初的结论 / 什么时候推的 / 什么否定了它 / 现在的结论在哪。**

> ⚠️ **本文件里没有一条是当前有效的结论。** 想知道现在的事实，去每条最后那个链接。

---

## 1 · "传输中断可恢复" 和 "掉电中断（S4）"这两条已验证结论

| | |
|---|---|
| **当初的结论** | 进程被杀 → app 区半写 → `BOOTLD-INVALID` → 重烧恢复；写到 49152 字节时拔电 → `Reset cause: POR` + `metadata present` + `App signature invalid` |
| **什么时候推的** | 2026-08-16 之前，**都是真机实测，观测本身没错** |
| **什么否定了它** | SDRAM staging 落地。那两个时刻**flash 压根没被碰过**，所以观测虽然真实，描述的已经是一个不存在的失败语义 |
| **现在的结论** | 原来那个 S4 拆成 S4a（传输中拔电，预期旧 app 照常启动）和 S4b（擦写阶段拔电，唯一真会留下半写 app 区的窗口）。[../test/CASE-DESIGNS.md](../test/CASE-DESIGNS.md) |

★ **这一条是这个文件最值得读的一条**：一个正确的实测结论可以因为**系统变了**而失效，而它看起来和其他 ✅ 一模一样。这就是 `$PROD/docs/STATUS.md` 加「证据还成立吗」那一列的直接原因。

## 2 · "备份域误报的根因是 witness 寄存器读到错值，未查明"

| | |
|---|---|
| **当初的结论** | `iap_auth_report_backup_domain()` 报"备份域丢失"，根因是 witness 读到错值，机理不明 |
| **什么时候推的** | 2026-08-15 ~ 08-16 |
| **什么否定了它** | 2026-08-17 加了一行写回读 —— `Witness write-back: 56424154 (want 56424154) - stuck, so it is lost later`。**写得进去，是事后被抹掉的**。顺着这条线找到 app 侧占了同一个寄存器 |
| **现在的结论** | **跨仓备份寄存器撞车**：bootloader 的 witness 和 app 的 nonce 计数器都占 `DR2`。witness 已挪到 `DR3`。`$PROD/docs/design/ARCHITECTURE.md` 的寄存器分配表 |

★ **真正的缺陷比表象严重得多。** 表象是"误报备份域丢失"；实际是**每次经过 bootloader，`DR2` 被写成 `0x56424154`，app 随后重复发放同一批 nonce 编号** —— 重放保护只剩 `tick` 在撑。

## 3 · "witness 是新加的寄存器，第一次执行必然不匹配，报出来是正确行为"

| | |
|---|---|
| **当初的结论** | 那条告警是正常的首次运行现象，之后就不会再报 |
| **什么时候推的** | 2026-08-16 |
| **什么否定了它** | 2026-08-17 又报了一次，而 counter 从上次的 35 涨到了 **39** —— 不是首次运行 |
| **现在的结论** | 同上第 4 条 |

⚠️ **这条的教训是"看起来能解释一切的假设最危险"。** "第一次当然没值"解释了当时看到的全部现象，而且听起来完全合理。

## 4 · "app 的 `[BOOT] millis=` 这行根本到不了 RS232 端子"

| | |
|---|---|
| **当初的结论** | 打印那一刻 PB10 还是低的，MAX3221 处于 shutdown、电荷泵停转，物理上产生不出 ±5V。所以以前在串口看到的 `[BOOT]` **一定不是从 C05/C06 出来的** |
| **什么时候推的** | 2026-08-16，**逐行核实代码后断言的** |
| **什么否定了它** | 2026-08-17 实测：它就在 COM5 上，也就是 RS232 端子 |
| **现在的结论** | **代码事实没错，错的是"所以发不出去"这一步推论。** 关键数字是 `millis=12` —— bootloader 刚把 PB10 拉低，**电荷泵靠外部电容的余电还没塌下来**，12 毫秒后仍能产生合规电平。banner 是蹭着余电挤出去的。[../work/ISSUES.md](../work/ISSUES.md) 的 `ISS-B1` |

★ **这是本文件里最该记住的一条**：**逐行核实代码得出的"代码事实"可以完全正确，而从它推出的下一步结论完全错误。** 代码说 PB10 是低的 —— 对。代码不知道电容里还有电。

⚠️ 它是靠时序巧合工作的，不是设计出来的路径。app 启动只要慢过电荷泵的衰减时间，这行就没了，**而没有任何东西保证那个时间**。

## 5 · 乱码字节的根因："bootloader 末次 printf 撞上 app 重新 `begin()` UART"

| | |
|---|---|
| **当初的结论** | `[BOOT]` 前那个乱码字节，是 bootloader 没发完的 printf 和 app 重新初始化 UART 撞车 |
| **什么时候推的** | 2026-08-16 之前 |
| **什么否定了它** | 核实 `Core/Src/main.c:87`：`__io_putchar` 是 `HAL_UART_Transmit(&huart4, &ch, 1, 10)`，**逐字节阻塞、末尾等 TC 标志**，函数返回时最后一个字节已完整移出。**没有"未发完的 printf"可撞**（115200 下单字节 87 µs，10 ms 超时碰不到） |
| **现在的结论** | 是收发器关断那一刻电荷泵塌陷，线电平从 mark 滑向 0V，接收端判成一个起始位。[../design/DECISIONS.md](../design/DECISIONS.md) 第 4 条（决定接受它） |

## 6 · 乱码字节的候选 ⚠3："sketch 打开收发器那一刻，电荷泵启动爬升"

| | |
|---|---|
| **当初的结论** | **我原先标的"最高把握"** —— 电荷泵启动时输出扫过整个范围，接收端判成起始位 + 帧错误 |
| **什么时候推的** | 2026-08-16 |

| **现在的结论** | 同上第 7 条 |

## 7 · 乱码字节的候选 ⚠1："DeInit 之后引脚浮空，芯片还开着"

| | |
|---|---|
| **当初的结论** | PC10（MAX3221 的 DIN）被释放成浮空而芯片还开着 → 输出跟噪声抖 |
| **什么时候推的** | 2026-08-16 |
| **什么否定了它** | 2026-08-17 把 `Disable_RX_RS232()` 挪到 `HAL_UART_DeInit()` **之前**（先静默再放引脚），重烧后 `[?[BOOT]` **一模一样还在** |
| **现在的结论** | 同上第 7 条。⚠️ **那次改动本身是对的并已保留** —— 让一颗还通电的收发器的输入悬空，本来就不该做 |

## 8 · "PG9 改成 input 会让 RESET 失效"

| | |
|---|---|
| **当初的结论** | 把 PG9（BOOT0 网）配成输入会让复位按钮失效。这条怀疑挂了很久 |
| **什么时候推的** | 更早的一次改动之后 |
| **什么否定了它** | 2026-08-18 **受控实验**（只改这一个变量）：6 次物理复位**全部** `Reset cause: PIN`，4 次正常进 app、2 次按住 BOOT0 进上传模式 |
| **现在的结论** | 真因是**当年同一次改动里还删掉了 `SystemClock_Config()`**，症状被错误归到 PG9 头上。[../design/HARDWARE-FACTS.md](../design/HARDWARE-FACTS.md) |

★ **教训：一次改动动了两个变量，症状就会被归给错的那一个，而且能挂好几个月。**

## 9 · "H2（主机 C 单测）只是缺一个环境，装上编译器就能补"

| | |
|---|---|
| **当初的结论** | H2 长期报 SKIP 是因为本机没有 host C 编译器。装上就行 |
| **什么时候推的** | 一直这么认为 |
| **什么否定了它** | 2026-08-17 装上 MinGW-w64 后第一次真跑，**它根本编不过**：`iap_auth.c:139: error: 'RTC_BKP_DR3' undeclared`。原因是修 DR2 撞车时把 witness 搬到 `DR3`，而 `host/bootloader_unit/stubs/rtc.h` 只定义到 `DR2`，没人跟着改 |
| **现在的结论** | 已修（stub 补齐 `DR0`–`DR7`），11 条断言全过。**教训进了 [../test/COVERAGE-GAPS.md](../test/COVERAGE-GAPS.md)** |

★ **一个长期 SKIP 的检查要当成"状态未知"，不能当成"缺一个环境就能补上"。** 环境补上那天可能会发现它早就烂了 —— **SKIP 掩盖的不是覆盖缺失，是这个检查本身已经不能运行了。**

## 11 · UART4 被重复占用的后果："静默掐掉接收，而发送看起来一切正常"

| | |
|---|---|
| **当初的结论** | `Serial4.begin()` 会**静默掐掉 `Serial_Test` 的接收**，发送不受影响 —— 是那种"能发不能收、查半天"的典型 |
| **什么时候推的** | 2026-08-16，**从 `uart_handlers[]` 每个外设只有一个槽位、最后一次 `begin()` 赢 推出来的** |
| **什么否定了它** | 2026-08-17 实测（修之前）：sketch 一调 `Serial4.begin(115200)`，`[BOOT]` 打到一半就断（`[?[B`），然后什么都没有 —— **app 直接挂死、UDP 发现不应答、以太网够不着，只能 ST-Link 擦掉 app 区才救回来** |
| **现在的结论** | **发送也死，而且板子失联。** E7 的严重性因此从"排查体验问题"升级为"用户一行普通代码就能让板子变砖（需 ST-Link）"。[../design/HARDWARE-FACTS.md](../design/HARDWARE-FACTS.md) |

★ **这一条差点让一个用例白跑**（`Serial` 不是 `Serial4`，拿 `Serial` 写的用例在未修的 core 上也会绿）。为什么会这样见 [../design/HARDWARE-FACTS.md](../design/HARDWARE-FACTS.md)；由此定下的规矩见 `$PROD/docs/CONVENTIONS.md`。

## 这些条目共同的教训

把这 13 条放在一起看，**错的地方集中在四种形状**：

| 形状 | 例子 | 怎么防 |
|---|---|---|
| **代码事实对，下一步推论错** | 第 6 条（PB10 是低的 ✅ → 所以发不出去 ❌） | 推论和事实分行写，标清哪行是哪个 |
| **小样本推出的结论** | 第 1 条（6 个字 → "开路"） | 说结论时带样本量 |
| **一次改动动了两个变量** | 第 10 条（PG9 + `SystemClock_Config`） | 受控实验，一次一个变量 |
| **从机制正确地推出了错误的后果** | 第 13 条（槽位会被抢 ✅ → 所以只丢接收 ❌） | 严重性靠实测定，不靠推理 |
| **正确的结论因为系统变了而失效** | 第 3 条（SDRAM staging 改了失败语义） | `$PROD/docs/STATUS.md` 的「证据还成立吗」列 |

⚠️ **还有一个跨条目的规律**：第 5 条和第 8 条都是"我标了最高把握的那个"被否定的。**把握程度和正确率在这批数据里没有相关性。**
