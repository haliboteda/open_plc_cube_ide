# 05 · 校准系数由上位机算出来

Type: prototype
Status: ✅ resolved（2026-09-13）—— 「算」做完了；「存」仍挂在 ISS-C1

## Question

AI / AO / RTC 的校准系数，**上位机怎么采点、怎么拟合、结果放哪**？

## 用户 2026-09-13 定的

原话：**「校正值存哪还没定，你先让上位机或者板子谁先把校正值算出来」**。

**算在上位机**（[DECISIONS.md 22 / 38](../../../design/DECISIONS.md)：计算和判定全在 PC，板子只报原始读数）。

---

## 做出来的

### 拟合在 Go 包里，不在页面里

`$TOOL/internal/ptcal/`。**理由和 `ptcheck` 是同一条**：产线跑一遍也要算同一件事，两处各写一份迟早会对同一批点得出不同的系数。页面通过 `/api/fit` 调它，CLI 以后直接 import。

### 拟合形状：直线，**但把残差摆在增益前面**

原来那句注释说得对 —— 「拟合用什么形状要靠一批真实数据定，现在编一个出来，等于给后面每块板埋一个说不清的偏差」。**这个反对意见是靠残差解掉的，不是靠忽略它**：

> **直线是能分开「零点偏差」和「增益偏差」的最小模型**，而分开这两个正是多点测量的全部理由。
> 真实响应要不是直线，**`max_residual` 会当场说出来**，而不是让拟合把弯曲度悄悄吸收进一个到处都错的增益里。
> **所以现在拟合直线是安全的：它没法掩盖自己选错了。**

实测（`/api/fit`）：五个点落在直线上 → 残差 **1.8e-15**；同样五个点带一点弯 → 残差 **0.5 mA**，并指出最差的点在哪一端。

### 四条边界，每条都会咬人

| 情况 | 怎么处理 | 不这么做会怎样 |
|---|---|---|
| **只有一个点** | 拒绝（`ErrTooFewPoints`） | 一个点分不出零点偏差和增益偏差，随便挑一个等于编 |
| **所有点设的是同一个值** | 拒绝（`ErrNoSpread`） | 线是竖的，再多点也recover不出增益 |
| **人跳过了某个点**（`null` / NaN） | 丢掉那个点，用剩下的算 | 一个 NaN 会让整条拟合变成 NaN，还不说为什么 |
| **正好两个点** | 算，但标 **`Exact`** | 两点必然落在自己那条线上，残差恒为 0 —— 那是算出来的，不是量出来的。**不标出来，人会从两个读数里读出一个完美校准** |

### `Correct()` 是反着来的

拟合说的是「让它出 X，实际出多少」；校准要的是反向：「要真的出 X，该让它出多少」。**方向弄反的校准会把误差翻倍而不是抵消，两边的数看着都合理** —— 所以有一条测试专门盯这个，不靠读代码。

### `Ideal()`：本来就准的板子不写系数

增益接近 1、零点接近 0 就报「不用补偿」。**不然每块板都会被写上一组 1.0000x 的系数，真正需要补偿的那些就淹了。**

## 还没做的

- **RTC 写校准**：`rtc.read` 的注释明写 *never writes it*。两个前置在 `ISS-C1` 和备份域占用那件事上。
- **把系数写回板子**：写的人 2026-09-14 定了是 **上位机**（用户原话：「上位机软件来写校准值」），经 JLINK 直写扇区，**固件不加写入命令**。剩下「写哪个扇区」等 `ISS-C1`。
- **拟合形状复核**：拿到一批真板子数据之后，看 `max_residual` 是不是一直贴着 0。**不是就得换模型**，那时这份的结论要重开。
