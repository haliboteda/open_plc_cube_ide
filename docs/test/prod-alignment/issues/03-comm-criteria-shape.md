# 03 · 五个通信口的判据形状

Type: grilling
Status: resolved（2026-09-13）—— 剩下「异常可恢复」一项仍开着

## Question

文档对 Ethernet / USB / CAN / RS485 / KNX 五个口统一写成「向固定设备**上传/下载文件，读取上传/下载速率并判定**」。现有实现是**回环计数 + 吞吐字节**。**判据按哪个形状定？**

## 现状（已核实）

| 口 | 会话做什么 | 帧里有什么 |
|---|---|---|
| `eth` | TCP server，`mode=echo/sink/source` | 连接数、收发字节、速率 |
| `usb` | CDC 会话，Device 侧 | 收发字节、`miss` |
| `can` | 按周期发帧，四种模式 | `seq/rx/miss`、`tx/rx_frames/junk`、`tec/rec/lec` |
| `rs485` | A/B 对上发号收号 | `seq/rx/miss`、`rxbytes`、`junk`、`overrun` |
| `knx` | `mode=frames` 发真 GroupValueWrite | 逐帧 `raw=` / `inv=` / `crc=` |

## 要定的

1. **以太网和 USB** 有吞吐概念，速率判据说得通。**门限是多少？** 文档写 TBD。
2. **CAN / RS485 / KNX** 没有「文件」也没有有意义的速率。建议判据改成：**发出去多少帧、收回来多少帧、误码/丢帧多少、总线错误计数器（CAN 的 `tec/rec/lec`、RS485 的 `overrun`）是否为零**。这个形状要不要定下来？
3. **异常可恢复** —— 文档 3.10 判定栏要求「全部配置接口通过且**异常可恢复**」，并记「误码/恢复时间」。**现在没有任何一项测「拔掉再插回来能不能恢复」。** 这一条要不要做、怎么做（拔线是人工动作）？


---

## ✅ 已定（用户 2026-09-13 同意）

落成 [DECISIONS.md 第 42 条](../../../design/DECISIONS.md)：

- **`eth` / `usb`** —— 保留速率判据 + 收发字节数，门限待定
- **`can` / `rs485` / `knx`** —— **帧数 / 丢帧率 / 总线错误计数器归零**（`tec`/`rec`/`lec`、`overrun`、`miss`）

## ⚠️ 仍然开着：异常可恢复

文档 3.10 判定栏要求「全部配置接口通过且**异常可恢复**」，并记「误码/**恢复时间**」。

**现在一项都没有。** 难在它本质上是人工动作（拔线、断电、拔卡），而人拔了之后还要回来汇报。更好的办法是**让上位机自己从帧里看出断了**（`conn` 掉到 0、`miss` 连增），再看它自己恢复用了多久 —— 人只要动手，不用汇报。**具体做法未定。**
