# 用例设计

**这里放用例的完整设计骨架和落地时的决定。** 从原 `TEST-PLAN.md` 拆出来（2026-08-22）—— 它的覆盖矩阵已经并进 [../STATUS.md](../STATUS.md)，覆盖缺口去了 [COVERAGE-GAPS.md](COVERAGE-GAPS.md)。

**判据和怎么跑不在这里，在 `$TOOL/TestTool/TEST-CASES.md`** —— 那是明文定的规矩（"贴着代码走，跨仓不搬"），也是对的：判据要跟着实现走。

**这份文件回答的是"这条用例为什么这么设计"** —— 那些不写下来就会在下次重构时被优化掉的决定。

## 三条原则

1. **测真实代码路径。** 需要"传输进行中"的用例把 IAPTool 当子进程拉起来跑真实烧写，不自己实现传输。
   > 教训：曾经手写的探测脚本能正常读到设备，掩盖了 `IAPTool` 自己 `SendCommandReadResponse` 的真 bug（单次读、不累积），直到用真实工具跑完整流程才暴露。**一次性脚本测的是它自己的逻辑。**
2. **加密逻辑 import，不重写。** 负向用例只把该错的那一处弄错，其余全用出货代码 —— S1 直接 import `IAPTool/iapcrypto`，只把那 64 字节签名弄错。
3. **反向用例和正向用例一样重要** —— "不该发生的事没发生"最容易漏，而且只在现场暴露（T1b「不该踢时没踢」、T4「拒绝状态没卡死」）。
4. **破坏性用例标 `destructive`**（会改变板子状态，比如 T3 烧完会重启进 app），`all` 模式自动排到最后 —— 否则它后面的用例全部假失败。

## 四层，由快到慢

**前一层不过就不要往下走。** 上板调试的每一轮都比主机测试贵一个数量级。

| 层 | 跑什么 | 要板子 | 耗时 | 一条命令 |
|---|---|---|---|---|
| **0 静态** | P1 P2 P3 P4 P6 | 否 | 秒 | `tools/selfcheck.py` 的一部分 |
| **1 主机** | H1 H2 H3 K1–K6 X1 X2 DG1 | 否 | 约 3 分钟 | **`tools/selfcheck.py`** |
| **2 构建烧写** | **BG1** + 尺寸门禁 | 是 | 分钟 | `tools/flash_bootloader.py` |
| **3 设备行为** | T/N/S、OW2 | 是 | 十分钟量级 | `TestTool all --ip=… --bin=… --password-file=…` |
| **4 人工** | AU1 OW1 OW3 S4a S4b M3 O1 | 是 + 人 | — | 见下面各条 |
| **—** | **P5**（编译所有 example） | 否 | **约 10 分钟** | `host/examples_build/build.py`，**故意不在 selfcheck 里** |

⚠️ **第 3 层要带 `--bin` 和 `--password-file`**，否则 S1/S2/T3 会因为缺参数而失败 —— 那不是板子的问题。

⚠️ **`TestTool all` 不含要人动手的用例**（AU1、OW1、OW3）。它们会被**点名跳过**而不是静默略过 —— 一个不吭声就消失的用例会被读成通过。

⚠️ **`BG1` 原来叫 `T0`**（2026-08-22 改名）。它不属于 T1–T4 那一系列：在另一个仓库、另一个文件、另一种性质（启动门禁不是设备行为用例），`TEST-CASES.md` 里根本没有 T0 这一条。见 [../ID-MAP.md](../ID-MAP.md)。

## 已实现的用例：落地时的决定

**这些用例已经通过**（结果在 [MEASUREMENTS.md](MEASUREMENTS.md)）。保留的是**为什么这么设计** —— 那些不写下来就会在下次重构时被"简化"掉的东西。

### S2 · 密钥不匹配

**为什么必须和 S1 分开**：混在一起测过一次，结果**把一次密钥轮换误判成校验代码的 bug**。两者现象都是"拒绝启动"，但一个是"没有任何密钥能产生的签名"，另一个是"格式完全正确但签方不对"。

| 决定 | 理由 |
|---|---|
| **签名由 `IAPTool sign` 子进程真实生成**，不在用例里自己签 | 和"传输不自己实现"同一条原则。自己签等于顺带在测本用例对 `r‖s` 编码的理解，而那是 X1/X2 的活 |
| **上传前先 `getpubkey`，确认板子信的不是这把临时密钥** | 临时密钥是每次现生成的，撞上是不可能事件。这道闸防的是**将来有人把它改成固定密钥文件** —— 那样用例不会失败，它会**真的把板子刷了** |

### S3 · 启动期签名失败（纯）

**为什么 S1 不能代替 S3**：SDRAM staging 之后，失败的上传**根本不碰 app 区**（就是 G1 那条）。所以 S1 的"下次启动被拒"那一半现在只发生在 metadata 和 app 不匹配的情况下，**证明不了"已装好的 app 每次启动都被重新校验"**。S3 是唯一直接测这条的。

| 决定 | 理由 |
|---|---|
| **改一个字节，不是擦掉整块** | 擦掉只能证明"发现 app 没了"。改中间一个字节才证明**哈希真的覆盖内容** |
| **先擦整个扇区再把改过的完整镜像写回**，而不是直接改那一个字节 | ⚠️ STM32H7 的 flash 每 256 位带 ECC，**同一个字编程两次**会让存下来的 ECC 变成两次的按位与，读出来就是不可纠正错误并把 CPU 打进 fault。那样 bootloader 会在算哈希时崩掉，而不是干净地报签名不过 —— 另一种失败，而且很难看懂 |
| **恢复路径先证明，再破坏** | 顺序反了的话，万一恢复镜像本身有问题，板子起不来而手上没有任何已知可用的东西 |

⚠️ **原来写的预期是错的，已改。** 原文说"**不是** `no valid application`（后者说明 metadata 也没了）"。实际上 `App signature invalid or absent` 和 `no valid application` **出自 `server_decide()` 的同一个分支**（`IAPServer/IAP_server.c:482-494`），必然同时出现。真正区分"app 坏了"和"metadata 也没了"的是 `Bootloader state:` 那行里的 **`metadata present` / `absent`**（`bootloader_state.c:155`）—— [../design/JOURNAL.md](../design/JOURNAL.md) 的表格一直是对的，是这里抄错了。

### AU1 · 板上 nonce 跨掉电不重复

**为什么值得做**：2026-08-17 刚发现过一个真实缺陷 —— bootloader 的 witness 和 app 的计数器都占 `DR2`，**每次经过 bootloader，app 就重复发放同一批 nonce**。这个用例能直接抓到那类问题，而当时是靠肉眼看日志发现的。

| 决定 | 理由 |
|---|---|
| **必须真断电，不能按复位** | 复位根本不碰备份域。只做复位的话，**一块 VBAT 电池已经没电的板子照样能通过** —— 而那正是这个用例要抓的板子 |
| **不让人按回车确认，而是看板子的 UDP 发现应答判断断电真的发生了** | 人的确认可以撒谎（也可以看错提示）。连续三次探测无应答才算断电，单次丢包不算 |
| **两路独立核对**：nonce 里的计数器 vs bootloader 自报的 `nonce counter = N` | 前者是从 nonce 前四字节推出来的，后者是直接读备份寄存器。两者对不上，说明其中一个不是在读它声称的东西 |

⚠️ **判据是「严格递增」不是「恰好加一」。** 跨掉电的 69→71 那个 gap 是对的 —— 中间那两次 challenge 是 `enter-bootloader` 自己的认证 reboot 消耗的。阶段**内**才要求恰好加一。

⚠️ **`nonce counter = N` 这行只在 bootloader 停下来的时候才打。** 板上有有效 app 时，上电那次会直接交权给 app，**根本走不到那句**。首次跑的时候脚本只翻上电日志，于是报"cross-check not available"，而那个数字其实就在紧接着的 `enter-bootloader` 日志里。已修：两份日志一起翻。

⚠️ **PowerShell 5.1 的坑，同一处**：`enter-bootloader.ps1` 全部用 `Write-Host` 输出，那是**信息流（6）不是成功流**。`2>&1 | Out-String` 抓到的是**空字符串**，而文字照样出现在控制台上 —— 看起来像板子没打印。必须用 `6>&1`。

### DG1 · 降级被拦下

**落地时比原设计多做的三件事**（都不是凑数）：

| 加了什么 | 为什么 |
|---|---|
| **每条都断言"板子有没有收到 `flash` 命令"**，不只看工具打了什么 | 一个打印了 `Downgrade refused` 之后照样上传的工具，能轻松骗过只看日志的检查。**C6 的真正主张是"板上的 app 没被碰"，只有板子那侧的日志能证明**。正向用例还要求 `IMAGE FULLY RECEIVED` —— 发出 `flash` 只说明闸门放行了，不说明传输活到最后 |
| **`same-version` 边界用例** | 比较是 `local >= remote`（`auth.go:248`）。这里差一位就会**禁止重刷同一个版本**，而那是所有人最常做的事 |
| **`ask-no-console` 强制喂管道 stdin** | `--downgrade=ask` 的行为取决于 stdin 是不是控制台。那条分支存在的原因是：从 IDE 启动时读 stdin 立刻返回 EOF，**以前会被报成"操作员拒绝"，而根本没人被问过**。不强制管道的话，这条用例的结果取决于脚本是怎么被启动的 |

⚠️ **DG1 覆盖的是工具侧的全部，而工具侧就是 C6 的全部。** bootloader 只在 `getversion` 报出已装版本，`expected_version` 存进 metadata 但从不比较 —— **换一个改过的工具照样能降级**。这不是缺陷，是 C6 当初就这么定的范围，写在这里是为了别让人以为板子在把关。

## 写新用例的骨架

**新用例先在这里写全骨架，再去 `$TOOL/TestTool/` 实现。** 实现后把判据写进那边，这里只留「为什么这么设计」。

| 栏 | 要求 |
|---|---|
| **目的** | 一句话。这条用例**唯一**证明的是什么 |
| **覆盖需求** | [../STATUS.md](../STATUS.md) 里的需求号。**填不出来的用例不该存在** |
| **前置条件** | 包括"需要什么硬件""需要人做什么" |
| **步骤** | 可以照着做，不需要再问 |
| **预期** | ⚠️ **写具体的日志文本，不写"应该正常"** |
| **验证方式** | 确切命令 |
| **实际结果** | ⚠️ **没写实际结果的就是没跑过。** 不要填"应该没问题" |

**要人动手的步骤按 🍍 规矩输出** —— 拔电、按 BOOT0、接线这类，脚本要用大标题 + 加粗 + 🍍 图标单独成段，理由放在指令块外面。

**能让脚本自己观察硬件的，就不要让人按回车确认。** AU1 就是这么做的：靠板子停止应答网络发现来判断电真的断了 —— 人只要动手，不用再回来汇报动手完了。
