# 协作约定

## ★ 用户说了一件事实，先落盘，再干别的

**用户在对话里说了一条事实、一个决定、或者"别做 X"** —— 第一个动作是**把它写进拥有它的那个文件**，然后回一句"改了哪几个文件"。**不是等收尾，是当下。**

**为什么必须当下**：对话不在 git 里。事实只活在对话里的话，**下一次读文档的时候，文档会把旧状态再讲一遍** —— 而文档是权威，所以 AI 会照旧状态继续干活，用户就得再说一遍。

> **2026-08-23 真实发生过，代价很直接。** 用户说了不止一次："SDRAM 好了，换了新的 upper deck；目前不要 `sdram_diag.c`。" 但 `STATUS.md` 写着 P0 是 D1 线、`ISSUES.md` 有 `ISS-B4`、`CLAUDE.md` 顶上一行红字、`RELEASE-NOTES.md` 一条 known issue、`investigations/sdram-d1.md` 整份都在讲它。**每次读文档都在提醒"这是 P0"**，于是 AI 反复把它当现状说回去。用户的原话：**"我都强调好几遍了，你还在反复的说 sdram 的事情。"**

**一条事实往往住在多个地方**，所以落盘要一次落全。判断标准很死：

> **搜一遍那件事的关键词。凡是把旧状态当现状讲的地方，都要改。改完再搜一遍，一处不剩。**

回话时**列出改了哪几个文件**。这不是汇报格式，是给用户一个能当场否掉的清单 —— 漏了哪个他一眼看得出来。

### 反过来也是规矩：别把用户已经定的事再问一遍

**用户说过的话，默认有效，不需要每次重新确认。** 想再问只有一种情况：**有新的实测证据和他说的相反** —— 那时要拿证据问，不是拿"我确认一下"问。

### 什么该问

| 情况 | 怎么办 |
|---|---|
| 用户说了一条事实 / 决定 | **落盘 + 回一句改了哪些文件。不要问。** |
| 用户说"不要 X" | **照做**，包括从构建里去掉、从文档里删。git 留着，能取回 |
| 两条指示互相矛盾 | 问，并把两条原话都摆出来 |
| 要动他没提到的东西（删文件、改构建、推别的仓库） | 问 |
| AI 自己觉得某个设计更好 | **在 [../work/ISSUES.md](../work/ISSUES.md) 里提，标"等用户定"。不要写进 [../design/DECISIONS.md](../design/DECISIONS.md)** —— 那份是"不要重开"，把建议放进去等于替他拍了板。2026-08-22 犯过一次 |

## 改动前先提方案

**任何写入项目文件的动作都要先说清"改什么、怎么改"，等同意再动手。** 诊断、调查、读代码不需要许可。

不要边讨论边改文件。

**给方案要给对比和取舍**，不要直接端出一个已经拍板的实现：列出可选路径、每条的代价和风险、推荐哪条及理由，由用户对比后决定。设计层面的取舍一律先摆出来；已经明确要做的小改动不用反复请示。

## 陈述任何问题都按这个骨架

**不论是回答提问、汇报发现、还是提方案，都要写全这五项**（2026-08-16 定）：

| | |
|---|---|
| **是什么** | 这个东西本身是什么 |
| **做什么用的** | 它为什么存在、在解决什么 |
| **在哪找** | `文件:行号`，能指就必须指 |
| **可能的影响** | 不修会怎样。**没有影响就直说没有**，不要为了显得重要而夸大 |
| **解决方案** | 怎么改 |

**只要存在多于一条路，就给对比表** —— 列出每条的代价、风险、推荐哪条及理由，由用户对比后决定。

## 脚本必须同时能在 Windows 和 Linux 上跑

**2026-08-19 定。** 目标是：换一台 Linux 机器，clone 下来、装好工具、填一份 `machine.ps1`，全套脚本照跑。

| 要做的事 | 用这个 | 不要用 | 为什么 |
|---|---|---|---|
| 判断平台 | `_common.ps1` 的 `$PLATFORM` | `$IsWindows` | 那是 PowerShell 6+ 才有的变量，**5.1 下是 `$null`**，判断会反过来 |
| 临时文件 | `Get-ScratchFile` | `$env:TEMP` | Linux 上该变量为空，`"$env:TEMP/x.out"` 会**塌成往文件系统根目录写** |
| 可执行文件 | `Get-GoBin` / `Get-IapTool` / `Get-ProgrammerCli` / `Get-CubeIdeExe` / `$EXE` | 硬写 `.exe` | — |
| 相对路径 | `/` | `\` | Windows 的 .NET 路径 API 接受 `/`，Linux 不接受 `\` —— `/` 是唯一两边都对的 |
| 平台目录名 | `$GOOS_DIR` / `$A15_DIR` / `$CUBE_PLUG` | 硬写 `windows` / `win` / `win32` | 同样三个平台，三套工具用三种叫法，集中在一处映射 |

**机器相关的路径一律进 `$TOOL/TestTool/config/machine.{ps1,py}`，而那两份是 `tools/init_machine.py` 生成的** —— 不手写，也没有模板可抄。

⚠️ **判断一个值该不该进配置：另一台同样系统的机器会不会有不同的值？** 不会就不属于那里 —— 那是平台派生量，归 `_common.ps1` / `common.py`。

⚠️ **遇到一个新的、只有本机知道的路径：加进 `init_machine.py` 的 `SETTINGS` 表**（连同探测方式和一段说明），不要硬编码，也不要猜。加进去它就会在每台机器上被自动找出来；写成一条"请手工填写"的说明，等于把这台机器的知识留在了这台机器上。

> **2026-08-20 删掉了 `machine.example.{ps1,py}`。** 它们和 `SETTINGS` 表是同一份清单的两个出处。而且模板那套"两个平台的值都给、删掉不用的那套"的用法，**忘记删是最常见的错误** —— 第一次在 Debian 上就踩了，表现是一堆互不相关的 MISSING，加上一句让人去查串口线的错误建议。

⚠️ **这条不止管脚本内部，还管 AI 会话怎么打命令。** 从一个仓库的会话里调另一个仓库的脚本（例如在 `open_plc_cube_ide` 里跑 `IAPTranfer_Tool/TestTool/tools/selfcheck.ps1`），**用相对路径 `../IAPTranfer_Tool/TestTool`，不要绝对路径**。第三节那张兄弟目录表已经把布局钉死了，相对路径换机器天然成立；绝对路径（`E:\WorkSpace\...`）只在这台机器上对，写进 `.claude/settings.local.json` 的 allow 列表里，换机器就是一条永远不会再命中的死记录。

**2026-08-23 实测：allow 列表不支持在字符串中间用 `*` 匹配任意前缀**，只有结尾通配符是文档确认支持的（`Bash(git *)` 这种）。所以"允许这条命令、不管前面的绝对路径是什么"这件事做不到，唯一可移植的办法就是从一开始就不在命令里写绝对路径。

⚠️ **提交进 `.claude/settings.json` 的 allow 规则只放不碰硬件、不改产品文件的命令**（读文件、跑静态检查、编译到本地产物）。**给板子刷固件、生成/替换密钥、往真实设备发升级命令**——这些哪怕本人已经批准过一百次，也不进那份**团队共享**的文件，因为一进去就是给每个 clone 这仓库的人默认放行，没人再会被问一句。这类命令要保留就放个人的 `.claude/settings.local.json`（本机专属、不进 git）。2026-08-23 把 `IAPTool.exe cdc/ether/genkey/sign` 和 `flash-bootloader.ps1` / `run-*.ps1` 这批从提交文件里挪回本地文件时发现的。

## 脚本和工具不许放临时目录

**任何要用第二次的东西，都直接写进仓库里的固定位置**，不要放 `%TEMP%` / scratchpad。

放临时目录的东西**换台电脑就全废**，而且不进 git、别人拿不到、下次会重写一遍。

| 东西 | 去哪 |
|---|---|
| 测试脚本、自动化工具（烧写、抓串口……） | `$TOOL/TestTool/tools/` |
| 一次性的探查命令（`grep` 一下、看个尺寸） | 不落盘，直接跑 |

> 2026-08-16 犯过：把自动烧写脚本写进 scratchpad，还硬编码了 `D:\ST\STM32CubeIDE_1.10.0` 和工作区绝对路径 —— 换电脑双重报废。**机器相关的路径一律进 `config/machine.ps1`。**

## 不要发散，不要假设场景

**每条建议背后都要有一个确实存在的场景。**

- ❌ 不要写"如果将来有人这样调用它就会出事" —— 除非那个调用者已经存在，或者已经有明确需求指向它
- ❌ 不要为了让问题显得值得修而虚构触发路径
- ✅ **当前影响为零就直说为零**，然后让用户自己决定要不要动

> 真实发生过（2026-08-16）：建议给 `Erase_FLASH` 补下界检查，理由是"将来若有调用者传低地址会擦掉 bootloader"。核实后 `Erase_FLASH` 全代码只有一个调用者，传的地址恒为 `IAP_APP_ADDRESS`，**那个调用者不存在，需求也不存在**。建议撤回。

## 不要想当然

涉及寄存器行为、引脚接法、链接脚本、跨仓绑定、工具链行为的结论，**先去原理图 / 数据手册 / 源码里核实**。核实不了就明说"这条没验证"。

> 教训：曾凭记忆断言"软件无法让 RESET 键失效"，查原理图后发现 PG9 和 MCU BOOT0 是同一条网络（见 [../design/HARDWARE-FACTS.md](../design/HARDWARE-FACTS.md)）。

## Todo 里写的"可能的影响"是推断，动手前先复现一次

模块文档里那一栏是**当初的判断**，不是实测。开工前花十分钟把症状复现出来，否则会按错误的严重性排优先级。

> 教训（2026-08-18，M5）：文档写的是"静默掐掉 `Serial_Test` 的接收，发送看起来一切正常"。实测是 **app 直接挂死、UDP 不应答、以太网够不着、IAPTool 救不回来，只能 ST-Link**。同一条风险，从"排查体验问题"变成"用户一行普通代码就能让板子失联"。按原描述它可以一直往后排。

⚠️ 反过来也成立：**复现不出来就别照着描述去修**。M5 那次第一版用例用了 `Serial` 而不是 `Serial4`，在**未修的 core** 上跑出了干净的通过 —— 差点改完 core、看到绿灯、宣布修好，而用例从头到尾没碰过那个缺陷。

## 判据要验"什么代码能真的跑起来"，不是"日志说了什么"

安全相关的功能尤其如此。

> 教训（2026-08-18，M1 第 4 步）：认领之后板子打印 `firmware must be signed by that owner`，`getpubkey` 也返回新密钥 —— 但 `fw_verify_signature()` 写死了 `fw_public_key`，**实际验签用的还是公开密钥，任何人签的固件照跑**。所有看得见的症状都正确，只有"用旧密钥签的 app 还能不能启动"这一条判据能发现。

## 不要擅自 dedup 或删除

代码要精炼；改动时顺手审视周围的既有代码。但是：

- 发现**重复或近似重复的功能** → **不要**静默合并或重构，问用户想怎么处理
- 发现**死代码 / 无用代码** → 可以删，但**删之前问**

**为什么**：这套系统横跨三个独立仓库、没有共享构建（见 [../design/ARCHITECTURE.md](../design/ARCHITECTURE.md)），**看起来的重复常常是刻意的** —— 同一个常量或算法被有意镜像到 bootloader / Arduino core / Go 工具三边。自动"清理"会静默搞坏另外两边。

## 注释只说目标

一行注释说明这段代码**要达成什么**即可。不解释原因、不展开推理、不写排查经过。非必要的注释直接删掉。

排查过程和设计权衡放到 `docs/` 或对话里，不要留在源文件。标了 TEMPORARY 的调试代码用完删干净。

## CubeMX 生成区不能手工改

代码必须写在 `/* USER CODE BEGIN *** */` … `/* USER CODE END *** */` 之间，否则从 `.ioc` 重新生成时会被 CubeMX 删掉。

> 真实发生过：一次重新生成删掉了 `main()` 里的 `SystemClock_Config();`，并把 `stm32h7xx_it.c` 的四个 naked fault handler 换回空 `while(1)`。

**USER CODE 块之外的东西，不要自己改 —— 报给用户，由他去改 `.ioc`。** 手工改生成区只是"这次能用"，下次重新生成全废；**只有 `.ioc` 才是单一事实源**。发现需要改动时，说清楚"哪个文件、哪一项、应该是什么值"。

找不到合适的 USER CODE 块，就把代码挪到 CubeMX 不生成的文件（如 `IAPServer/`）。CubeMX 自己会生成的调用（`MX_*_Init()`、`SCB_EnableICache()`）留在原位不要搬。

### 已经通过 `.ioc` 固化的

- `USBD_LPM_ENABLED` —— `.ioc` 里 `USB_DEVICE.USBD_LPM_ENABLED-CDC_FS=0`（2026-08-15）。此前每次重新生成都会变回 `1U`，那会让设备对主机声称支持 USB 2.0 LPM，而 `USBD_LL_Init()` 里 `lpm_enable = DISABLE` 根本没开这个功能 —— 声称了一个自己不会响应的能力。

### 重新生成后仍须复查（不在 USER CODE 块内）

- `.ioc` 里 PG9 的信号类型（见 [../design/HARDWARE-FACTS.md](../design/HARDWARE-FACTS.md)）
- `STM32H743IIKX_FLASH.ld` 的 `FLASH LENGTH` 必须是 **120K，不是 128K** —— 尾部 8K 是 owner 记录区（需求 C10）。⚠️ **看到 128K 不要“改回去”** ：那会让链接器把代码放进那 8K，把已经写在里面的所有权记录盖掉 —— 而那是静默的，板子会惄无声息地退回出厂根。理由见 [../design/OWNERSHIP.md](../design/OWNERSHIP.md)

四个 fault handler 已经做到重新生成安全：在 PD 块里把 CubeMX 生成的版本改名让路，在 USER CODE 1 里定义真正的 naked 版本。

## 设计不能限制用户的 app

**不论用户在 app 里怎么用这颗芯片，设计都必须依然正确。**

- 不能依赖 app 恰好关掉了某个功能（缓存、MPU、某块 RAM、某个外设）。典型反例：靠 `-DD_CACHE_DISABLED` 才正确的代码 —— 用户的 app 可能需要开缓存。
- 正确性靠**显式动作**保证（如显式 cache 维护指令），不靠"当前配置恰好如此"。
- **发现设计可能和用户 app 的自由度冲突时，必须主动提出来问**，不要自己判断"概率很低就算了"。

**为什么**：板子是给最终用户写 PLC 程序的，app 内容不在我们控制之下。任何"恰好能工作"的依赖就是埋雷 —— 已经吃过一次：DBP 位被前一步关掉导致以太网升级静默失败，而 CDC 路径只是恰好没踩到。
