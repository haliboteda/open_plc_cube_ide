# M2 · 证书链

**覆盖需求：[C11](../STATUS.md)**（板子从第一版就懂证书链，简单模式走同一条验证路径）、**[C12](../STATUS.md)**（撤销）。

**依赖 [M1](M1-owner-slot.md)** —— 证书要有一个根来验，那把根住在 owner 槽里。

> 设计推理在 [../design/OWNERSHIP.md](../design/OWNERSHIP.md)。这份只写落地。

## 一句话

板子里的公钥**从一开始就当"根"看**，不是当"固件签名者"看。工具默认发**自签证书**（叶 = 根，K 给自己作证）。用户体验等同单密钥；要切授权链时一条命令，**板子一个字节都不用改**。

## 全部价值在这一条上

> **简单模式也走验证书的路径，只是那张证书自签。**

板子的检查恒为「这张纸的章，是我认的根能核对的吗」，**没有自签特例分支**。

所以不存在"高级分支没人走、悄悄烂掉"。这是这套设计唯一真正买到的东西 —— 那张自签证书在安全上不增加任何东西，纯粹是 160 字节 + 一次验签。**代价要有意识地买。**

```
简单模式（K 给自己作证）              授权链（K 签 L）
板子里: K_pub                        板子里: K_pub  ← 一个字节没变
   │ 验证书签名                          │ 验证书签名
   ▼                                     ▼
cert{ pubkey=K_pub, sig=K签 }        cert{ pubkey=L_pub, sig=K签 }
   │ 取出 K_pub                          │ 取出 L_pub
   ▼                                     ▼
镜像签名 = K 签                       镜像签名 = L 签
```

⚠️ 升级到授权链之后那张自签证书**仍然有效**（它还是 K 签的），所以**根依然可以直接签固件**。这不是缺陷 —— 根持有者本来就是最终权威 —— 但别指望"升级后根就不能直接签了"。

## 证书住哪

**`0x081E0000` 的 M 记录里**，跟着 metadata 走。

理由：它只需要验证*当前那个* app，而 `journal_reclaim()` 只发生在 `save_metadata()` 内部 —— 擦完立刻就有一条新 M 记录带着新证书写进去。**只有 owner 根和撤销状态需要免疫 reclaim**，证书不需要。

## 分步计划

| 步 | 做什么 | 验什么 |
|---|---|---|
| 1 | 定证书格式（含 `serial`、`format_ver`），`_Static_assert` 锁尺寸 | 主机侧能生成能解析 |
| 2 | 工具侧：签名时同时发一张自签证书 | 老 bootloader 忽略多出来的字段，仍能正常烧写（**向后兼容**） |
| 3 | bootloader：验证书 → 取叶公钥 → 验镜像。**只有这一条路径** | 简单模式全流程通过；改坏证书则拒绝 |
| 4 | 工具侧：`K 签 L` 的授权链模式，一条命令 | 板子不重烧，直接接受 L 签的镜像 |
| 5 | 撤销（C12） | 撤掉一个 serial 后那张叶子失效；**撤到只剩一个根时拒绝继续撤** |

## 还没定

| | 影响 | 归属 |
|---|---|---|
| **`serial` 谁分配、怎么保证不重复** | 它是撤销的唯一依据。两张叶子拿到同一编号，撤销一张会**连坐**另一张 | 工具侧。做第 5 步之前必须定 |
| 会话认证换不换成证书 | 换了能消掉固定密码的三边镜像 + [../design/DEFERRED-DESIGNS.md](../design/DEFERRED-DESIGNS.md) 里的产线单板密钥 | ⚠️ **要动 core**，成本差一个数量级 |

`serial` 的候选：根私钥旁边放个计数器文件／时间戳／用户指定。**不阻塞 M1，做证书那步再定。**

## 成本提醒

[../design/OWNERSHIP.md](../design/OWNERSHIP.md) 的位置表最后一列全是"不用改 core" —— **那是对 owner 槽说的，不是对证书说的**。

> 会话认证一旦改成证书，core 侧 `iap_keyderive` 必须跟着改。**两件事成本差一个数量级，应该影响实施顺序。**

所以：**先做 M1（不碰 core），证书的镜像签名部分也不碰 core，只有会话认证那一步才碰。** 那一步可以无限期推后。

## 验收

用例还不存在，做之前先写骨架。至少：

- 简单模式（自签证书）全流程通过
- 授权链模式（K 签 L）通过，**板子未重烧**
- 证书签名被改 → 拒绝
- 证书里的叶公钥和镜像签名不配 → 拒绝
- **反向用例**：撤销到只剩一个根时，再撤一次必须被拒（R4，防永久变砖）

最后一条来自 ESP32 Secure Boot v2 的真实教训，官方文档自己写着 aggressive revoke "could also brick the device permanently if all the keys are revoked"。
