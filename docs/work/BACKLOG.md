## 每份模块文档怎么写

统一骨架，和 `$PROD/docs/CONVENTIONS.md` 的五项一致：

| 段 | 内容 |
|---|---|
| **是什么 / 做什么用的** | 一段话说清 |
| **覆盖哪条需求** | 指向 `$PROD/docs/STATUS.md` 的需求编号。**填不出来的模块不该立项** |
| **在哪找** | `文件:行号`，能指就必须指 |
| **不做会怎样** | 没影响就直说没有 |
| **设计思路** | 已经想清楚的部分照抄进去，落地时不用重想 |
| **方案对比** | 多于一条路就给表：代价 / 风险 / 推荐 |
| **分步计划** | 每步一个可验证的中间状态 |
| **验收** | 做完跑什么用例才算过。用例没有就先去 [../test/CASE-DESIGNS.md](../test/CASE-DESIGNS.md) 写骨架 |
| **已否决** | 讨论过并砍掉的路，连理由一起 |

⚠️ **模块文档里"可能的影响"那一栏是当初的判断，不是实测。** 开工前先把症状复现一次，否则会按错误的严重性排优先级；反过来，**复现不出来就别照着描述去修**。
