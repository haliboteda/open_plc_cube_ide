# M3 · app 侧能用 SDRAM

**覆盖需求：[E5](../STATUS.md)**

**状态：✅ 完成（2026-08-17）** —— 库、验收（19/19 实测）、两个 example、用户文档都有了。

> **要做，而且要封装好，用户直接调封装好的能力就行。** —— 产品负责人 2026-08-17

这句话把 M3 从"要不要做"变成"做成什么形态"，**而且否掉了原来那个方案**。下面「原设计」一节保留是为了记住它为什么不够。

## 是什么

板载 64MB 外部 SDRAM（AS4C32M16SB-7BIN），映射在 `0xC0000000`。

| | |
|---|---|
| **bootloader 侧** | 接收 CDC/以太网镜像的暂存区，校验通过后才写 flash。**已在用，是 SDRAM staging 的基础** |
| **app 侧** | **目前没有用途，也用不了** |

## 在哪找

| | |
|---|---|
| bootloader 初始化 | `Core/Src/main.c:201`（`MX_FMC_Init()`），实现和上电时序 `Core/Src/fmc.c:44-126` |
| bootloader 交权时关掉它 | `IAPServer/IAP_server.c:501` 的 `HAL_DeInit()` |
| core 侧 | `core:variants/STM32H7xx/H743/` 下 `.c/.cpp/.h` **全搜零命中**；`ldscript.ld:41-55` 的 `MEMORY` 块也没声明 SDRAM |

## 不做会怎样

app 完全用不了这 64MB。用户想跑大数据缓冲（数据记录、大点表、图像）就只能用片内 512K。

**这是产品能力问题，不是 bug。** 所以第一步是确认需求，不是写代码。

## "封装好"改变了什么

原设计是**让用户自己在 linker script 的段里声明大数组**，要求用户懂下面「原设计」一节那三条硬约束，还要记得**自己 `memset`**，否则读到的是上次掉电前的残留。

**"直接调封装好的能力"意味着这些全部不能落到用户头上。** 具体转化成三条：

| 原设计要用户做的 | 封装之后 |
|---|---|
| 在 linker script / 段属性上做对三件事 | 用户碰不到，库里定死 |
| FMC 初始化的时机 | 库负责，用户不用管什么时候能开始用 |
| ⚠️ **自己 `memset`**，否则是极难查的间歇性 bug | **库负责清零** —— 这是封装最大的价值，那个坑直接消失 |

⚠️ **代价**：清 64MB 要时间（100MHz、16 位总线，粗估几十毫秒到上百毫秒量级，**未实测**）。所以"要不要默认清零、还是提供一个不清零的快速路径"是要定的第一个设计问题。

## 四个待定问题 —— 2026-08-17 已定并落地

| 问题 | 定成什么 | 依据 |
|---|---|---|
| **API 形态** | 分配器：`SDRAM.begin()` → `SDRAM.alloc(n)` | 见下「为什么不给链接脚本段」 |
| **能不能释放** | **不能**，只增长的 bump 分配器 | PLC 程序在 setup 里一次分配、用到关机。给个堆只会多出碎片和一种没人要的失败模式。**将来要加真分配器不破坏这个 API，反过来不成立** |
| **自检失败怎么办** | `begin()` 返回 `false`，之后 `alloc()` 一律返回 `nullptr` | 不 `Error_Handler()` 停机 —— 是不是致命由应用决定，库不替它决定 |
| **清 64MB 要多久** | **实测 91 MB/s，清满 64MB ≈ 701 ms**（清 16MB 用 175 ms，`begin()` 本身 1.4 ms） | 所以默认清零对常见尺寸够便宜（1MB ≈ 11ms），但**大块要留出路**，于是有了 `allocUninitialized()` |

**落地**：`core:libraries/OpenPLC_SDRAM/`，外加变体头里补的 `HAL_SDRAM_MODULE_ENABLED`（原来没开，库会静默走 fail-closed 分支）。

## 为什么最终不给链接脚本段

原方案让用户自己声明 `__attribute__((section(".sdram_bss")))` 的大数组。**它给用户四种出错方式，三种是静默的** —— 前三种就是下面那张表里的三条硬约束各违反一次，第四种是**忘了内存不是零**。

**最后一条最毒**：数组里是上次掉电前的残留，程序"大部分时候看起来是对的"。

**一个只能从 `alloc()` 拿到的地址，不可能在控制器起来之前被碰** —— 因为 `begin()` 没成功时 `alloc()` 就返回 `nullptr`。四个坑不是被写进文档，是**不存在了**。

## 原设计（段声明方式）—— 仍然是底层做法，只是不再直接暴露给用户

| | 做法 | 理由 |
|---|---|---|
| **bootloader** | **裸地址** `(uint8_t*)0xC0000000`，**保持现状不动** | 一次性 staging；不希望链接器往里放任何东西；SDRAM 在 startup 时还没初始化，**声明它反而危险** |
| **app / core** | **写进 linker script，用 `(NOLOAD)` 段** | 用户会声明大数组，需要链接器做冲突检测和溢出报错。裸指针的话两个库都用 `0xC0000000` 会静默互踩 |

app 侧三个硬要求：

| | 要求 | 不这么做会怎样 |
|---|---|---|
| 1 | 段必须标 **`(NOLOAD)`** | 段会进 `.bin` —— 一个 1MB 数组让固件镜像涨 1MB |
| 2 | 段必须放在 **`_sbss` … `_ebss` 之外** | startup 的清零循环会扫到它。**清零发生在 FMC 初始化之前，往未初始化的 SDRAM 写 = 故障** |
| 3 | ⚠️ **只能是 BSS 风格，不能有初值** | `.data` 风格的段会被 startup 的拷贝循环在 FMC 之前写 |

**可抄的写法**：`core:variants/STM32H7xx/H743/DAISY_SEED.ld:74`（`SDRAM (xrw) : ORIGIN = 0xC0000000, LENGTH = 64M`）和 `:217-227`（`.sdram_bss (NOLOAD)`）。

⚠️ **那是上游 Electrosmith Daisy Seed 板子的脚本**，`core:boards.txt:50` 写死了 OPEN-PLC 用 `ldscript.ld`，构建里没引用它。只是一份可抄的写法，不是现成的配置。

## ⚠️ 原来"必须写进用户文档"的那条代价，封装之后应该消失

原文写的是：**这些变量不是零初始化的，用户必须自己 `memset`**，否则数组里是上次掉电前的残留，"看起来大部分时候是对的"—— 一类极难查的间歇性 bug。

**封装的意义就在这里：这条不该再是用户的负担，应该是库的职责。** 如果最后的 API 仍然要求用户自己清零，那就等于没封装，方案要重做。

> 反过来讲，如果为了性能确实要提供不清零的路径，**那个路径必须在名字上就说明白**（比如 `allocUninitialized()`），不能是默认行为。

## 验收 —— 2026-08-17，19/19 通过

用例在 `$TOOL/TestCase/onboard/sdram/SDRAM_Acceptance/`，编排 `tools/run-sdram.ps1`。

| 验什么 | 结果 |
|---|---|
| `begin()` 之前 `alloc()` 返回 `nullptr`、`ready()` 为假 | ✅ **这是"四个坑不存在了"的直接证据** |
| `begin()` 成功、幂等 | ✅ |
| ⚠️ **拿到的 1MB 全零** | ✅ **封装的核心价值。原方案里这一条是用户的义务** |
| 1MB 写满读回一致、地址在 SDRAM 窗口内、8 字节对齐 | ✅ |
| 两次分配不重叠，且第二次的清零不破坏第一块 | ✅ |
| `available() + used() == 64MB` | ✅ |
| 超容量分配、零长度分配都返回 `nullptr` | ✅ |
| **`.bin` 不因为缓冲变大**（86,172 B，只比空 sketch 多约 2.4KB 的库代码） | ✅ 缓冲是运行时拿的，根本不在镜像里 |

**测量**（不是判据，是拿来定 API 的依据）：`begin()` 1.4 ms；清 16MB 175 ms → **91 MB/s**；折算 64MB **≈ 701 ms**；`allocUninitialized()` 0 µs。

⚠️ **SDRAM 自检失败时的行为没有实测** —— 要制造一个坏 SDRAM 才能测，暂时只有代码路径（`begin()` 返回 false）。

## 已否决

**让用户自己在 linker script 段里声明大数组。** 那是原设计，2026-08-17 因"要封装好、用户直接调"被否 —— 它把三条链接脚本约束和一条 `memset` 义务全压给用户，其中 `memset` 那条漏了就是极难查的间歇性 bug。

⚠️ 但**段声明本身仍然是底层实现**，只是不再是用户接口。上面「原设计」那节的三条硬要求**一条都不能少**，做库的时候照样要满足。
