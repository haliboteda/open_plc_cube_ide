## 当时推到的结论（是推断，不是实测；没有被证实也没有被否定）

**D1 这一段导通极弱**：SDRAM 的 D1 输入端拿到的不是干净的逻辑电平，而是**近期驱动值缓慢漂移后的混合**。

这一条同时解释三件事：写入序列相同则结果相同（确定性）；只与同一根线的邻近历史相关（不涉及其他线）；对 1.5 倍时钟变化不敏感（时间常数远大于两种位周期）。

**第二轮测量把这条推断收窄成两个互斥候选，两个都还没被排除：**

| 候选 | 支持它的 | 反对它的 |
|---|---|---|
| **A. 远端没接上**（MCU 焊球或走线断/高阻） | 释放时间只有同端口邻居的 58% —— MCU 这头看不到远端的电容 | 电容小应该让**两个方向都变快**，实测下降方向反而更慢 |
| **B. 有一条通往高电平的漏电路径** | 写 0 只有 13.4% 成功、写 1 有 90.7%；上升快、下降慢，正是被往上拖的形状 | 下降那一列落在分辨率地板上，证据强度不够 |

**分开 A 和 B 只需要跑一次浮空测试** —— 代码当时写好了、编译过、**一次都没在板子上跑过**（写完时板子已断电，之后就换板了）。要复现那次排查，先从 git 取回 `sdram_diag.c`。

实测结果（32768 个 16 位字，先全部写完再全部读回）：

| 测量 | 结果 | 说明什么 |
|---|---|---|
| 逐位 | bit1 错 **15745 / 32768 = 48.0%**，其余 15 位 **全 0** | 和第一轮一致 |
| 写 0 / 写 1 分开 | **写 0 只有 13.4% 读对，写 1 有 90.7% 读对** | ⚠️ **和第一轮的 56.3% / 62.7% 差得很远**，见下面那条警告。这一版的形状是"这根线被往高处拖" |
| 驻留扫描（同一个值连写 1/2/4/8/16 遍） | 48.6% → 48.3 → 48.0 → 45.8 → **43.6%** | 确实随驻留变长而下降，**但只降了 5 个百分点** → 整定时间**远大于** 16 个总线周期（160 ns） |
| **释放时间**（内部上拉当电流源，同一端口 7 根线同时释放、同时采样） | D1 **452**，同端口 6 个邻居 700 / 751 / 751 / 751 / 852 / 852（均值 776）→ **D1 是邻居的 58%**，落在邻居分布之外 | D1 这根网络**从 MCU 这一端看电容明显偏小**。单位是"采样序号 ×100"，一次采样 15.03 个 CPU 周期 ≈ 37.6 ns（按 CPU 400 MHz 推），所以 D1 约 170 ns、邻居约 292 ns。**比值不依赖时钟假设，绝对值依赖** |
| 下降方向 | 除 D1（103）和 D13（268）外全部是 0 | ⚠️ **落在分辨率地板上，不可解读** —— 一次采样已经走完大半，别拿这一列推结论 |

⚠️ **同一个端口内比较才有效。** 端口 E 的 9 根好线释放时间从 652 到 1404，跨了 2.2 倍 —— 走线长度和引脚位置本身差别就这么大。D1 的 6 个参照物必须是**同一个 GPIO 端口、同一次释放、同一段代码采的样**（D0 D2 D3 D13 D14 D15 恰好都在 GPIOD），否则 58% 这个数没有意义。

⚠️ **上升更快 + 下降更慢，"电容偏小"解释不了。** 电容小应该两个方向都变快。另一种同样能解释的机理是**这根线上有一条通往高电平的漏电路径**（它同时解释写 0 大量失败、写 1 大量成功）。这两种要分开，需要第四项测量：**驱动之后不加任何内部上下拉、放开、等 2 ms 再读** —— 只有自身电容的线会保持原样，有漏电的线会被拖走。40 kΩ 的内部上拉会赢过弱漏电，所以第一轮"内部上下拉完全跟随"那条**看不见这件事**。

## 位置还没定，但候选从四个减到两个

原先四个候选（MCU 焊球 / 走线过孔 / SDRAM 焊球 / SDRAM 的 DQ1 输入单元）在 CPU 看来完全一样。释放时间这一项**第一次把它们分成了两组**：58% 这个数指向"MCU 这一端看不到远端"，也就是**前两个**候选；如果浮空测试反过来说是漏电，那嫌疑回到球下的污染或桥连，两端都可能。

⚠️ **万用表和示波器都用不上。** 这条网络两端都在 BGA 球下、中间无器件、整条数据总线上没有一个测试点，详见 [../../design/HARDWARE-FACTS.md](../../design/HARDWARE-FACTS.md) 的「这条总线上没有任何可以下探头的地方」。

## 当时给硬件那边的三条请求（**已作废：换板了**）

1. **局部冷冻或加热 U6，然后 U1，我们同时在线读 bit1 错误率**（`sdramlive` 就是为这个写的）。错误率跟着某一颗变 → 故障在那一颗球下；两颗都不敏感 → 嫌疑转向内层走线。**这是唯一能非破坏性地缩小到某一颗芯片的办法。**
2. **X-ray 看 U1 的 ball L14 和 U6 的 ball B9**：空洞、裂纹、少锡、球形异常。这块板 8-18 还是好的，"从好变坏"更像焊点疲劳。
3. **第二块板到货后先跑一次 BG1** —— 新板子也失败就是设计/工艺问题，正常就是个体故障。**这是唯一能区分这两者的实验**，成本一次上电。

⚠️ **这三条一条都没做** —— 2026-08-23 直接换了 upper deck。**所以那块坏板子如果还在，它仍然是唯一的样本，上面的证据也还在。** 想真的定位根因，第 1 条（冷热喷剂 + `sdramlive`）仍然是最有效的。

## 当时的影响（现在都解除了）

`Core/Src/fmc.c` 的注释被证实：坏 SDRAM 里暂存的镜像**校验失败，app 区根本不被碰**，板子始终安全。

| **BG1**（启动门禁） | 直接失败，3/3 复现 |
| **S4a / S4b** | 跑不了 —— 任何上传都停在 checksum，所以 **E8 一直停在 ⬜** |
